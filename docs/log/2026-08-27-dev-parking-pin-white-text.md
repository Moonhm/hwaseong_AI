  나오잖아 몇대 이렇게. 이거 다 하얀색 글씨로 바꿔줘 지금 어떤건 검은색인거같은데

## 0. 이 문서를 남기는 이유

**이건 하루 전 감사가 내린 접근성 결정을 뒤집는 작업이다.**
근거를 안 남기면 다음 감사가 같은 이유로 또 뒤집는다. 실제로 그 감사가
`_pkLum()` 이라는 상대휘도 계산기까지 만들어 넣었던 자리다.

WORKFLOW.md §0 기준으로는 '색 조정' 처럼 보여 커밋 메시지로 끝낼 뻔했는데,
「나중에 누가 왜 그랬는지 궁금해할 것인가」를 대보면 명백히 궁금해할 자리다.

## 1. 무엇이 문제였나

핀 배경은 잔여 비율에 따라 빨강→초록으로 변한다.

```
pinColor(p) → hsl(Math.round(ratio * 118), 72%, 42%)
```

색상(hue)만 0→118 로 움직이고 명도는 42% 고정이다. 그런데 **같은 명도라도
색상에 따라 실제 밝기가 크게 다르다** — 노랑은 밝고 파랑 계열은 어둡다.

2026-08-26 감사는 WCAG AA(4.5:1)를 맞추려고 글자를 뒤집었다.
밝은 핀에는 검은 글씨(`#111827`), 어두운 핀에는 흰 글씨.
계산은 맞았다. 그런데 결과가 **핀마다 글자색이 달라 보이는** 화면이었고,
사용자가 그걸 지적했다.

## 2. 되돌리기 전에 대비를 실측했다

`hsl(h,72%,42%)` 위 흰 글씨의 대비비:

| hue | 여유율 | 흰 글씨 | 검은 글씨 | 감사가 고른 것 |
|---:|---:|---:|---:|---|
| 0 (빨강) | 0% | **6.47** | 2.72 | 흰 |
| 24 | 20% | **4.58** | 3.84 | 흰 |
| 30 | 25% | 4.06 | **4.34** | 검정 |
| 60 (노랑) | 51% | **2.11** | 8.33 | 검정 |
| 90 | 76% | 2.47 | 7.15 | 검정 |
| 114 (초록) | 97% | 2.62 | 6.72 | 검정 |

고정색: 미운영 `#9CA3AF` 흰 2.54 · 만차 `#EF4444` 흰 3.76.

**여유가 25% 를 넘는 구간부터 흰 글씨가 AA 를 못 넘긴다.** 최악은 노랑 2.11:1.

### 배경을 어둡게 해서 푸는 길은 애초에 없다

명도를 낮춰 보면:

| 명도 | 흰 글씨 최저 대비 |
|---:|---:|
| 42% (현재) | 2.11 |
| 38% | 2.58 |
| 34% | 3.18 |
| 30% | **3.99** |

30% 까지 낮춰도 3.99 라 4.5 를 못 넘긴다. 그러면서 핀은 눈에 띄게 어두워진다.
**'색을 눌러서 흰 글씨를 살린다' 는 선택지가 존재하지 않는다** — 감사가
글자를 뒤집는 쪽으로 간 이유도 이것이다.

## 3. 그래도 흰색으로 간 근거 셋

**하나. 이 핀에서 상태를 알리는 1차 수단은 글자가 아니라 색이다.**
빨강이면 자리가 없고 초록이면 넉넉하다는 것을 색이 먼저 말한다.
숫자는 그 보조다. 숫자가 조금 흐려도 정보가 사라지지 않는다.

**둘. '가장 가까운 주차장' 모드 핀(`.np-pill`)은 처음부터 흰 글씨 고정이었다.**
같은 데이터를 그리는 두 핀이 서로 다른 글자색을 쓰고 있었다 —
오히려 그쪽이 어긋난 상태였다. 이제 맞는다.

**셋. 사용자가 실제 화면을 보고 지적했다.** 계산상 옳은 것과 눈에 옳은 것이
갈릴 때, 이 앱은 눈 쪽을 따른다.

## 4. 그림자로 보완했다 (사용자 후속 지시)

글자색을 되돌리지 않고 읽히게 하는 길이 하나 더 있다.

```css
.pk-count { color: #fff; text-shadow: 0 1px 2px rgba(0,0,0,0.45); }
```

진하기는 '약간' 으로 잡았다. **0.45 보다 진하면 11px 짜리 작은 글자가 뭉개진다.**

`.np-pill` 쪽에도 같이 넣었다. 그 핀의 대수 `span` 에는 클래스가 없어
`.np-count` 를 새로 붙였다(`js/map.js` `_makeNpParkPin`).
🅿️ 이모지는 별도 `span` 이라 그림자가 걸리지 않는다.

> 두 핀 중 한쪽에만 그림자를 넣으면 **또 갈린다.** §3 의 둘째 근거를
> 스스로 무너뜨리는 셈이다. 한쪽을 만지면 반드시 다른 쪽도 본다.

## 5. 걷어낸 것

- `pkTextOn(color)` — 인라인 글자색을 만들던 함수. 이제 아무도 안 쓴다.
- `_pkLum(color)` — `pkTextOn` 만 쓰던 상대휘도 계산기. 함께 죽는다.

`.pk-count` 의 인라인 `style="color:..."` 를 빼서
`css/20-map.css` 의 `.pk-count { color:#fff }` 가 그대로 살게 했다.

**`pkInkOn()` 은 남긴다.** 방향이 반대다 — 흰 원판 위의 'P' 글자라서
밝은 핀 색을 그대로 쓰면 안 보인다. 그쪽은 명도 28% 로 눌러 쓴다.

## 6. 실측

`pinHtml()` 을 11개 상태로 직접 렌더해 `getComputedStyle` 로 쟀다.

```
여유 0%(만차) 10% 20% 25% 35% 50% 65% 80% 100% · 미운영 · 만차
  → 전부 rgb(255, 255, 255)
  → 흰색 아닌 것 0건
.pk-count 그림자  rgba(0, 0, 0, 0.45) 0px 1px 2px
.np-count 그림자  동일
pageerror 0 · check.sh exit 0
```

## 7. 하지 말 것

- **글자색을 다시 뒤집지 마라.** 대비 수치만 보면 뒤집는 게 맞아 보인다.
  §2 의 표가 그 수치이고, §3 이 그럼에도 흰색으로 간 이유다.
  읽기 어렵다는 말이 나오면 **그림자 쪽을 조정해라** — 반경을 키우는 편이
  진하기를 올리는 것보다 낫다(작은 글자가 덜 뭉개진다).
- **두 핀 중 하나만 만지지 마라.** `.pk-count`(`css/20-map.css`)와
  `.np-count`(`css/40-quiz.css`)는 같은 데이터를 그린다.
- **`_pkLum` 을 되살리지 마라.** 되살릴 이유가 생겼다면 그건 §3 을 뒤집는
  것이므로 사용자에게 먼저 물어야 한다.
