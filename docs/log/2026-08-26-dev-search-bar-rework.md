## 2. 버린 방법 ① — 홈 구 칩 4개

### 왜 칩으로 갔나

지도에는 이미 구 칩이 있었다. 홈에도 달라는 요청이었으니 **같은 물건을 같은 모양으로
옮기는 것**이 가장 짧은 답으로 보였다. 색도 지도 칩과 같은 보라(`#7C3AED`)로 맞췄다 —
카테고리 칩이 파랑이라 같은 파랑을 쓰면 '검색 필터의 한 종류'로 읽힌다.

새 검색 로직은 **한 줄도 만들지 않았다.** `pickHomeGu(gu)` 는 검색창에 구 이름을 써
넣고 기존 `doHomeSearch` 를 부른다. 이미 친 검색어는 유지하고 구만 갈아 끼웠고
(`'항'` + 만세구 → `'만세구 항'`), 재클릭은 해제였다.

### 왜 되짚었나

사용자 지시가 정면으로 뒤집었다 —

> "이 구역을 거기 밑에 칩으로 두라는게 아니고 저기에 **검색하면 뜨도록** …
> 지도로 연동돼서 바로 이어갈수있도록."

요청을 잘못 읽었다. 사용자가 원한 것은 *검색창에서 구를 고를 수 있게* 였지
*검색창 밑에 버튼을 붙여라* 가 아니었다. 칩으로 만들면 고를 수 있는 것이
**네 개로 고정**되고, 화면에서 44px(패딩 8 + 최소 높이 36)을 상시 차지하며,
검색어와 칩이라는 **입력 경로가 둘**이 되어 계속 동기화해야 한다(실제로
`homeSearchInput`·`clearHomeSearch` 두 곳에 동기화 호출을 끼웠다).
검색 결과로 내면 셋 다 없다.

## 3. 지역을 '검색 결과'로 — 부분 일치를 더한 이유와 그 한계

`splitGuQuery` 는 `'동탄구'`·`'동탄'` 처럼 **온전한 이름(또는 '구' 뗀 형태)** 만
잡는다(`js/district.js:232-241`). 칩이 있을 때는 그걸로 충분했다. 칩을 없애고 나니
치는 도중에는 아무것도 안 뜬다 — 한글은 조합 중 상태가 길어 `'동'` 만 쳐진 순간이
반드시 지나간다. 그래서 `GU_NAMES` 를 앞부분만 겹쳐도 제안하는 분기를
`doHomeSearch` 에 더했다(`js/home.js:444-460`).

문구도 바꿨다. `'동탄구 지도에서 보기 / 그 동네 화면으로 이동해요'` →
`'동탄구 전체 보기 / 지도에서 이 동네만 봐요'`. 옛 문구 `'지도에서 보기'` 는 바로
아래 지역명 결과의 부제와 **똑같은 말**이었다(`js/home.js:465` 의 `_REGIONS` 가
`sub: '지도에서 보기'`) — 한 목록 안에서 다른 두 동작이 같은 문구를 달고 있었다.
누르면 `setGuView` 가 `setBounds` 로 카메라를 그 구 범위에 맞출 뿐이다
(`js/district.js:112-115`). 레이어를 구로 거르지는 않는다 — 무엇을 그릴지는 카테고리
칩이 그대로 정한다(같은 파일 `:110-111` 주석). 화면에 들어오는 것만 그 구로
한정된다는 뜻이라 '이동' 보다 '이 동네만 보기' 가 사실에 가깝다. 같은 함수의
토스트도 `'화면 안의 것만 보여요'` 다(`:116`).

확인하다 하나 알게 됐다. 조건이 둘인데 **둘째가 첫째에 완전히 포함된다.**

```js
if (g.indexOf(q) === 0 || g.slice(0, g.length - 1).indexOf(q) === 0) {
```

`g.slice(0, -1)` 은 `g` 의 접두사이므로 그것의 접두사는 `g` 의 접두사이기도 하다.
node 로 `동/탄/병/만/효/동탄/병점/만세/효행/동탄구/ㄷ/빈문자/가` 를 넣어 비교했더니
**둘째 조건만 걸리는 입력은 0건**이었다. 무해하지만(한 `if` 안이라 중복 push 도 안
난다) 군더더기인 것은 사실이므로 적어 둔다.

같은 확인에서 **접두사만 잡는다**는 것도 드러났다. `'탄'` 을 치면 동탄구가 안 뜬다.
`includes` 로 바꾸면 되지만 그러면 `'구'` 한 글자에 네 개가 전부 떠서 결과 상자를
다 먹는다. 접두사로 둔 것은 선택이다.

## 4. 버린 방법 ② — 홈 검색창 슬림·반투명

`afe80b5` 는 `.search-bar` 를 패딩 11/16→9/15px, 테두리 1.5→1px, 배경
흰색→`rgba(255,255,255,0.92)` + `backdrop-filter: blur(10px) saturate(1.3)` 로
바꿨다. 홈과 지도가 **같은 클래스 하나**를 쓰고 `.search-bar--map` 은 위치만 바꾸는
구조였다. 12분 뒤 사용자가 잘랐다 — *"홈에 있는 검색은 그대로 둬야지"*.

(메시지에 적힌 '글자 14 → 13.5px' 은 **diff 에 없다.** `afe80b5` 시점의
`.search-bar input` 은 그대로 14px 이고, 13.5px 은 오히려 `003ff0e` 가
`.search-bar--map input` 에 새로 준 값이다. §8 과 같은 종류의 메시지 오류다.)

되돌린 방식이 중요하다. **모양을 버린 게 아니라 자리를 옮겼다.** 반투명·블러는 뒤에
무엇이 있어야 값을 한다. 홈 검색창 뒤에는 단색뿐이고(`css/00-base.css:58`
`body { background: var(--bg) }`, `--bg: #F5F6F8`) 얻은 것은 높이 44 → 40px 이
전부다(각 커밋 실측치). 지도는 뒤에 타일이 있고 검색창이 지도를 가리는 물건이므로
반투명·블러가 거기서는 제 값을 한다. 그래서 슬림·반투명 전부를 `.search-bar--map`
안으로 내리고 `.search-bar` 는 원래대로 뒀다. `3d81c30` 시점의 `.search-bar` 규칙
6줄(당시 `css/00-base.css:140-145`)과 지금 `css/00-base.css:145-150` 을 텍스트로
비교하면 **한 글자도 다르지 않다.**

되돌리면서 **홈이 잃은 것**도 있다. `afe80b5` 가 넣었던 `.search-bar:focus-within`
(입력 중 테두리를 파랗게)은 `.search-bar--map:focus-within` 으로만 남았다. 지금 홈
검색창은 포커스 표시가 없다. 일부러 뺀 게 아니라 '원래 모양' 에 그게 없었기
때문이다 — **되돌림이 좋은 것까지 같이 가져갔다.**

`.search-bar--map` 은 `.search-bar` 에서 받아 쓰던 `padding: 9px 15px; gap: 9px` 를
스스로 갖게 됐다(`css/00-base.css:158`). 두 규칙이 이제 독립이다.

### 곁다리 — 관광/생활 토글 위치

`afe80b5` 는 관광/생활 토글을 즐겨찾기·최근 본 **위**에서 **아래**로 내렸다. 이
토글이 조작하는 대상(`#home-tourism`/`#home-living`)이 바로 아래인데 사이에 섹션
둘이 끼어 있었다. 41분 뒤 `515a8d2` 가 간격을 다시 잡았다 — 아래 패딩 14→6px,
콘텐츠 `margin-top` 16→2px, 위쪽 `margin-top` 18→28px. **아래를 붙이고 위를 띄워야**
어느 쪽에 속한 버튼인지 읽힌다.

## 5. 검색창이 둘이 됐다 — 왜 로직은 한 벌인가

`_SR_DOM` 은 창 이름 → 엘리먼트 id 넉 장(input·clear·results·bar)의 표이고
`_srWhere` 는 지금 활성 창이다(`js/home.js:397-410`).

```js
function homeSearchInput(val, where) { where = where || 'home'; … }
```

`where` 를 안 넘기면 홈이다. 그래서 **`js/home.js` 바깥의 기존 호출부는 한 줄도
안 고쳤다** — `index.html:61` 의 홈 입력창은 지금도 `homeSearchInput(this.value)`
그대로고 `js/boot.js` 의 `closeHomeSearch()` 도 그때는 그대로였다(`where` 가 붙은
것은 뒤의 `b4736f2` 다). 고친 것은 `home.js` 안쪽뿐이다.
검색 로직은 `doHomeSearch` 하나에 몰려 있다(`js/home.js:422-553`, 132줄). 지도용을
한 벌 더 만들었으면 데이터 소스가 늘 때마다 두 곳을 고쳐야 하고, 한 곳을 빠뜨리면
'홈에서는 나오는데 지도에서는 안 나오는' 차이가 조용히 생긴다.

### 홈 결과 상자를 재사용하지 않은 이유

`#home-search-results` 는 `#page-home` 안에 있고(`index.html:42`, `:66`)
`css/00-base.css:70-77` 이 `.page { display: none; position: absolute }` /
`.page.active { display: block }` 다. **지도 탭이 켜져 있는 동안 홈 페이지는
`display:none` 이라 그 안의 결과 상자는 어떤 방법으로도 안 보인다.**
`position:absolute` 로 끌어내는 것도 답이 아니다 — 부모가 `display:none` 이면
자식은 렌더 트리에 아예 없다. 그래서 `#map-search-results` 를 `#page-map` 안에
따로 뒀다(`index.html:547`).

같은 함정을 이날 다른 데서 실제로 밟았다 — `cc9f94c` ①의 '음식점 업종 필터 8칩이
절대 안 보였다'가 `#rs-filter-bar` 를 `display:none` 인 `#lc-filter-bar` **안에**
넣어 버린 사고다.

`_srWhere` 가 전역이라 '엉뚱한 창에 그려질' 여지가 있는지 봤다. `doHomeSearch` 가
맨 위에서 `_srWhere = where` 를 넣고 같은 호출 안에서 동기로
`renderHomeSearchResults` 까지 가므로 그 사이에 다른 값이 끼지 못한다.

## 6. `.search-bar` 아래 여백 14px 과 `-15px` 은 짝이다

사용자 지적: *"디자인이 지금 밑에 바로 안달리고 막 중간이 비거든?"*

인접 형제의 마진은 상쇄된다. `.search-bar` 의 `margin-bottom: 14px` 과
`.home-search-results` 의 `margin-top` 이 만나 `14 + (음수)` 가 실제 간격이 된다.

| `margin-top` | 실제 간격 | 보이는 것 |
|---|---:|---|
| `-6px` (종전) | **8px** | 결과 상자가 검색창에서 떠 있다 |
| `-15px` (지금) | **-1px** | 1px 겹쳐서 테두리가 한 줄로 보인다 |

`-14px` 이 아니라 `-15px` 인 이유가 그 1px 이다. 결과 상자는 `border-top: none` 이라
윗변이 없지만 검색창 테두리 1.5px 은 남으므로, 간격을 0으로 맞추면 두 상자 사이에 그
선이 한 줄 남는다. 1px 을 더 당겨 결과 상자 밑으로 밀어 넣었다(`003ff0e` 메시지 ④ 는
이것을 "두 줄로 보인다" 고 적었는데, 결과 상자에 윗변이 없으니 정확한 말이 아니다).

이 8px 은 원래도 있었는데 구 칩을 끼우면서 눈에 띄었다. CSS 값으로 계산하면 칩이
있을 때는 **14 + (8 + 36) − 6 = 52px** 이다(`.home-gu-row` 패딩 8 + `.home-gu-chip`
`min-height: 36`). 계산값이고 그 중간 상태를 실측하지는 않았다.
두 값이 짝이라는 것은 `css/00-base.css:185-189` 주석에 박아 뒀다.

**지도 쪽은 이 짝과 무관하다.** `#map-search-results` 는 두 클래스를 함께 다는데
(`.home-search-results` + `.map-search-results`), `css/20-map.css:411-416` 의
`.map-search-results { position: absolute; top: 50px; margin: 0 var(--px) }` 가
`margin: -15px` 을 덮는다(같은 특이도, `20-map.css` 가 뒤에 로드된다). `#page-map`
기준 절대 위치라 마진 상쇄가 애초에 일어나지 않는다.

대신 `top: 50px` 은 **당시 검색창 높이(`top:12` + 38)에 손으로 맞춘 값**이라
자동으로 따라오지 않는다 — 뒤에 입력 글꼴이 13.5px→16px 로 올라가(`58d4939`)
검색창이 높아졌으므로 지금 이 값은 검색창 아랫변과 정확히 맞지 않는다.
몇 px 어긋나는지는 **측정하지 못했다**(§9).

## 7. `backdrop-filter` 경고에 해당하는 자리가 실제로 있다

`css/00-base.css:155` 에 "`backdrop-filter` 는 부모에 `filter`/`transform` 이 걸리면
무력화된다" 는 주석을 남겼다. 그 조건에 들어맞는 자리가 있다 — `css/00-base.css:91-94`
의 키프레임이 `transform: translateX(18%)` 로 시작하고 `:101-104` 가 그것을 `.page` 에
0.26초 물린다(`js/nav.js:81` 이 들어오는 페이지에 클래스를 붙인다). `.search-bar--map`
의 부모는 `#page-map` 이다(`index.html:524` → `:539`). 즉 **탭이 들어오는 0.26초 동안
지도 검색창의 부모에 `transform` 이 걸려 있다.** 마지막이 `transform: none` 이라 끝나면
풀린다. 그동안 블러가 실제로 꺼져 보이는지는 브라우저를 못 띄워 **확인하지 못했다**(§9)
— 주석의 전제까지 재현하지는 못했다.

## 8. 되짚어 보니 커밋 메시지가 틀린 곳 — `?v=` 두 건

세 커밋의 `?v=` 를 실제 diff 와 대조했다.

| 커밋 | 메시지 | 실제 diff | |
|---|---|---|---|
| `3d81c30` | …651 → **…653** | …651 → **…653** | 일치 |
| `afe80b5` | …656 → **…657** | …656 → **…658** | **틀림** |
| `003ff0e` | …661 → **…663** | …661 → **…664** | **틀림** |

둘 다 메시지가 실제보다 하나 작다. 메시지를 먼저 쓰고 `?v=` 를 한 번 더 올린 것으로
보인다(`afe80b5` 직전 `css/10-content.css` 만 …57 이었던 흔적이 있다).
**동작에는 영향이 없다** — 실제 파일이 더 큰 값이라 캐시는 정상으로 깨지고,
`tools/check.sh` 5-b(`version_guard`, `tools/check.sh:166-181`)도 'js/·css/ 를 고친
최신 커밋이 `index.html` 도 함께 고쳤는가' 만 볼 뿐 메시지 숫자를 읽지 않는다.
그래도 메시지를 믿고 되짚으면 틀리므로 적어 둔다.

## 9. 검증 — 그날 한 것과 오늘 못 한 것

그날 실측치는 각 커밋 메시지에 있다(Chromium 390×844). 요지는 칩 66×36px, 지도에서
`'궁평항'` 4건에 홈 결과 오염 없음, 되돌린 뒤 구 칩 0개 · 홈 검색창 44px · 결과 간격
**8px → -1px** · `'동'` 한 글자에도 지역 제안이 맨 위. 세 번 다 `check.sh` FAIL 0.

**하루 뒤인 오늘 다시 재려다 실패했다.** 이 컨테이너의 `chrome-headless-shell` 이
`libnspr4.so` 를 못 찾아 뜨지 않는다. 그래서 §6 의 "지금 지도 검색창 높이" 는
**측정하지 않았다**고 적었다. 이번에 새로 확인한 것은 전부 저장소를 직접 읽거나
node 로 돌린 것이다 — `git show --numstat` 줄 수, grep 잔존 0건, `GU_NAMES` 순서,
부분 일치 조건의 중복(node 전수), `.search-bar` 블록의 텍스트 동일성, CSS 마진 산술.
지도 카메라 동작(`setGuView`)은 카카오 SDK 가 안 떠서 **코드 경로로만 논증**했다.
