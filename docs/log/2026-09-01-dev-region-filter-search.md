  이용할수있어야해."*

## 1. 칩은 달지 않았다 — 그게 사용자 지시와 맞다

전수 감사(`v16`)가 이 건을 **착수 금지로 올려 뒀다.** 이유가 있었다.

```
08-25 16시대   배포 로그에 「4구 + 13읍면 17필터 — 사용자 승인」
08-26 08:54    003ff0e  홈 검색 원복 + 지역을 칩이 아니라 검색 결과로
08-26 11:49    f872314  "지도에 위에 4개 구 칩 이랑 전체 칩도 지워버려"
```

**승인보다 칩 제거 지시가 나중이다.** 지금 화면의 활성 지역 칩은 0개이고(`data-gu` 6건은
전부 HTML 주석 안), `docs/log/2026-08-26-dev-search-bar-rework.md` §10 이 그 결론을
「이제 구 진입로는 검색뿐이다」로 적어 뒀다. 17개 칩을 새로 다는 것은 이 지시를 뒤집는 일이라
개발 Claude 가 단독으로 정할 수 없었다.

사용자가 **「그냥 통합검색에서 이용할 수 있어야 해」**로 정해 줬다. 08-26 지시와 같은 방향이다.
**`index.html` 의 칩 주석은 그대로 뒀다.**

## 2. 라벨링(항목 필터링)은 안 했다 — 데이터가 못 받친다

「읍·면으로 항목을 걸러 준다」도 가능한 해석이라 먼저 쟀다.

| 데이터셋 | 주소에서 읍·면이 읽히는 비율 |
|---|---:|
| PLACES 243건 | 144건 (59%) |
| 주차장 131건 | 45건 (34%) |
| 음식점 3,754건 | 1,439건 (38%) |

주차장은 **셋 중 둘이 안 읽힌다.** 이 상태로 「우정읍 주차장」을 필터로 걸면 있는 것을 없다고
답한다. **없는 것보다 나쁘다.** 그래서 이번 범위는 **「그 지역을 지도에서 보여 주는 것」**이다.

> 오늘 `b13` 이 고친 것은 **구(區)** 인식이다(주차장 131/131). 읍·면은 별개 축이고 위 수치가
> 그 실측이다. 구 단위 필터는 이미 `_inGu` 로 동작한다 — 「동탄구 약국」 은 지금도 걸러진다.

## 3. 실제로 고친 것 — 좌표 4곳이 엉뚱한 데를 가리키고 있었다

`_REGIONS` 에 13읍면 중 12개가 이미 있었다. 그래서 「매송 한 줄만 더하면 끝」인 줄 알았는데,
**넣기 전에 있는 값부터 검산했다.** `b12`(제부도·서신이 바다 위)를 오늘 겪었기 때문이다.

거리만 보면 안 걸린다. **「그 점이 그 읍·면 안에 떨어지는가」**로 봐야 한다 —
반경 2km 안 가맹점 중 해당 읍·면 비율과 최근접 가맹점의 소속으로 판정했다.

| 읍면 | 최근접 가맹점 | 반경 2km 안 비율 | 판정 |
|---|---|---:|---|
| 팔탄 | **향남** 0.25km | **1%** (4/648) | ❌ 눌러도 향남이 뜬다 |
| 우정 | **장안** 0.52km | 13% (11/87) | ❌ |
| 비봉 | **팔탄** 0.69km | 23% (21/90) | ❌ |
| 마도 | **남양** 1.19km | 28% (8/29) | ❌ |
| 나머지 8곳 | 자기 읍·면 | 80~100% | ✅ 그대로 뒀다 |

팔탄이 가장 심하다 — 반경 2km 안 648곳 중 팔탄은 4곳뿐이다. **'팔탄' 을 검색해 누르면
향남 한복판이 떴다.**

넷 다 해당 읍·면 가맹점 좌표 **중앙값**으로 바꿨다(서신을 오늘 고친 것과 같은 방법).
교체 뒤 다시 검산해 **75~100%** 로 전부 자기 읍·면에 떨어지는 것을 확인했다.

| | 새 좌표 | 검산 |
|---|---|---|
| 매송면 (신규) | `37.249635, 126.923605` | 97% (74/76) |
| 우정읍 | `37.083703, 126.817283` | 75% (372/493) |
| 비봉면 | `37.236712, 126.871244` | 100% (221/221) |
| 마도면 | `37.201181, 126.776409` | 90% (133/147) |
| 팔탄면 | `37.160652, 126.890443` | 100% (332/332) |

## 4. '봉담읍' 이라고 치면 0건이던 것

`_REGIONS` 의 이름이 `'봉담'` 인데 `_tokScore` 는 **이름이 토큰으로 시작하는지**를 본다.
`'봉담'.indexOf('봉담읍')` 은 `-1` 이라 **접미사를 붙여 친 검색이 전부 0건**이었다.
읍·면은 사용자가 '면'·'읍' 까지 붙여 치는 것이 자연스러운데도 그랬다.

13읍면 각 항목에 `full`(`'봉담읍'`)을 달아 **별칭으로 넘기고 표시명으로도 쓴다.**
`'봉담 지역'` 보다 `'봉담읍'` 이 정확하다. `full` 이 없는 항목(동탄·제부도 등)은 예전 그대로다.

## 5. 검증

`js/district.js` · `js/data.js` · `js/convenience.js` · `js/home.js` 를 vm 에 올려
실제 `_REGIONS` 와 `splitGuQuery` 로 돌렸다.

```
13읍면 × 2가지 표기(짧은 이름 / 정식 명칭)  → 26/26 전부 1건씩 매칭  실패 0
4구 (동탄구·병점구·효행구·만세구)            → splitGuQuery 가 전부 인식
어간만 친 '효행'·'만세'                      → 각각 효행구·만세구로 인식
```

4구는 **손댈 필요가 없었다** — `splitGuQuery` 가 정식 명칭과 어간을 이미 둘 다 받는다.

```
bash tools/check.sh              통과 · FAIL 0 / WARN 0
bash tools/check.sh --precommit  통과 · ?v= …160 → …161
python3 tools/check_data.py      통과 · 35,427건 대조 / FAIL 0
```

## 6. 남은 것

- **읍·면 단위 항목 필터링**은 위 2절의 인식률(34~59%) 때문에 안 했다. 하려면 주소 정비가
  먼저다 — 주차장 86건·음식점 2,315건에 읍·면이 없다.
- `WORKFLOW.md` 에 이 기능의 상태가 **한 줄도 없었다**(§0 이 경고한 「로그에만 있는」 상태).
  §27-I 에 현재 상태를 적었다.
