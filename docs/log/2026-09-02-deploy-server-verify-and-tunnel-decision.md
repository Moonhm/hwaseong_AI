- 날짜: 2026-09-02
- 담당: 배포 Claude
- 커밋: `PENDING`

  이어서 지시 — *"네임드 터널로 갈라면 url 사야하니까 힘들고 플로우 한번 읽고 로그 작성해."*

## 0. 「적용했다」와 「지금 돈다」는 다르다

08-31 에 최적화 6가지를 넣고 실측까지 붙여 뒀다. 그런데 그 사이에 **재부팅 두 번**과
**서버 재기동 한 번**이 있었다. 문서에 적힌 값은 그때의 값이고, 물어보신 것은 **지금**이다.
그래서 문서를 인용하지 않고 전부 다시 쟀다.

## 1. 결론부터 — 서버·Flask 이상 없고, 최적화도 켜져 있다

```
flask 3.1.3 · waitress 3.0.2 · requests 2.34.2 · brotli 1.1.0
모드: waitress (스레드 8) · 프리워밍 list 131건 · realtime 145건
단일 요청 응답 3 ms
```

| 항목 | 어떻게 쟀나 | 결과 |
|---|---|---|
| 압축 | `Accept-Encoding` **8케이스 전수** | `br,gzip`→br · `gzip`→gzip · **`gzip;q=0`→무압축** · `br;q=0,gzip`→gzip · `*`→br · `identity`→무압축 — **전부 의도대로** |
| 압축 캐시 | `/healthz` | hit 189 / miss 50 · 47개 1.34MB |
| 캐시 헤더 | 5개 경로 대조 | `?v=` js→`immutable` · `.json`→`3600`(immutable 없음) · `img/`→`no-cache` · **404→헤더 없음**(`b19`) · `index.html`→`no-cache` |
| 상류 캐시 | 실제 호출 2회 | `x-cache: fresh` · 145건 · **사용중 114곳**(폴백 아님) |
| 첫 화면 | 31개 자원 실측 | 913,129 B → **292,666 B (−67.9%)** |

`gzip;q=0` 이 무압축으로 떨어지는 것을 특히 확인했다. 개발 Claude 가 `5f5a6b4` 에서
「q 값을 보고 0이면 뺀다」로 고친 자리이고, 여기서 틀리면 **클라이언트가 못 푸는 인코딩을
보내 화면이 통째로 깨진다.**

## 2. 그 전에 — **내 측정 도구가 두 번 고장났다**

이 절이 이 로그에서 제일 값이 있다. 둘 다 **서버가 이상해 보이는 결과**를 냈고,
둘 다 원인은 서버가 아니었다.

### ① 터널 너머로 재서 Cloudflare 동작을 우리 서버 동작으로 읽을 뻔했다

처음에 공개 URL 로 쟀더니 이렇게 나왔다.

```
Accept-Encoding: br, gzip   →  gzip      ← br 을 넣었는데 gzip 이 온다
Accept-Encoding: gzip;q=0   →  gzip      ← 명시적으로 거부했는데 gzip 이 온다 (!)
```

두 번째 줄은 **버그로 보이는 결과**다. 그대로 「q=0 처리가 깨졌다」고 보고했으면
개발 Claude 가 멀쩡한 코드를 뜯어봤을 것이다.

**Cloudflare 가 중간에서 다시 압축한다.** §0 의 「**어디서 쟀는지를 적으십시오**」가
정확히 이 자리다. 로컬(`localhost:8080`)에서 다시 재니 8케이스 전부 정상이었다.

### ② `awk` 의 `IGNORECASE` 가 이 환경에서 안 먹었다

로컬로 옮겨 재니 이번엔 **전부 「무압축」** 으로 나왔다. `/healthz` 는 gzip 239건을
세고 있는데 말이 안 된다. 헤더를 가공 없이 그대로 떠 보니 —

```
Content-Encoding: gzip
Content-Length: 27420
```

**있었다.** `awk -v IGNORECASE=1` 은 gawk 기능인데 이 컨테이너는 **mawk** 라 무시된다.
그래서 `/^content-encoding/` 이 `Content-Encoding` 을 못 잡았다. 터널 쪽에서는
HTTP/2 가 헤더를 소문자로 정규화해 우연히 매치됐고, 그래서 **①에서는 값이 나오고
②에서는 안 나온** 것이다.

> **자를 먼저 의심해야 한다.** 「서버가 이상하다」는 결과가 나왔을 때 두 번 다
> 이상했던 것은 자였다. 08-31 이 세운 규칙이 「재라」와 「어디서 쟀는지 적어라」였는데,
> 여기에 하나가 더 붙는다 — **결과가 놀라우면 도구부터 검증한다.**

## 3. 발견 — **brotli 는 실사용자에게 도달하지 않는다**

로컬에서 재니 brotli 가 완벽하게 돈다.

```
원본        101,845 B
gzip         27,420 B  (−73.1%)
brotli q9    24,584 B  (−75.9%)
```

그런데 **터널 너머는 언제나 gzip** 이다. 코드가 아니라 경로 문제인지 확인하려고
`/healthz` 의 누적 카운터를 봤다.

```
br 6회 · gzip 257회        ← br 6회는 전부 방금 내가 로컬로 친 시험분이다
```

결정적인 확인을 하나 더 했다. **브라우저와 똑같이** `Accept-Encoding: gzip, deflate, br, zstd`
를 넣어 **터널로** 요청하고, 그 전후로 `br` 카운터를 읽었다.

```
6 → 6      안 올랐다
```

**Cloudflare Quick Tunnel 이 원본에 br 을 아예 요청하지 않는다.** 우리 서버는
`Accept-Encoding` 을 정확히 처리하는데, 터널이 그 헤더를 gzip 으로 정규화해서 넘긴다.
즉 **br 분기는 실트래픽에서 한 번도 탄 적이 없다.**

08-31 개발 Claude 로그가 *"edge 가 br 을 안 해 준다 → **원본이 해야 한다**"* 로 맺었는데,
**원본이 해도 안 된다.** 터널이 요청 자체를 안 넘기기 때문이다. 그때 잰 「첫 화면 −7.8%」는
로컬 값이고 **사용자에게는 전달되지 않고 있다.**

### 그래도 고칠 것은 없다

| | |
|---|---|
| 코드 | **정상이다.** 되돌릴 이유가 없다 |
| 비용 | 압축은 ETag 로 캐시돼 파일당 1회다. 안 타는 분기가 있어도 부담이 없다 |
| 언제 살아나나 | **터널을 바꾸면 저절로** 산다. 지금 실이득은 gzip 몫(−67.9%)이고 그건 제대로 나가고 있다 |

`WORKFLOW.md` §12 「핵심 현황」에 **현재 사실로** 올렸다 — 다음 사람이
「brotli 넣었는데 왜 br 이 안 보이지」로 시간을 쓰지 않게.

## 4. waitress A/B 는 **재현하지 못했다** — 반증이 아니라 측정 불가

08-31 기록은 `Flask 개발서버 208.7ms → waitress 110.3ms (1.89배)` 다.
같은 조건을 만들려고 `--dev` 를 8081 에 띄워 나란히 쟀다.

```
waitress(8)   중앙값 281.5 ms   (최소 197 / 최대 295)
Flask --dev   중앙값 289.1 ms   (최소 211 / 최대 348)
→ 1.03배
```

**이걸 「waitress 가 무용하다」로 읽으면 안 된다.** 서버 단일 응답이 **3ms** 인데
집계가 285ms 로 나온다 — **클라이언트(파이썬 GIL·urllib)가 병목**이라 서버 차이가
묻힌다. curl 로 바꿔도 132~548ms 로 튀었다.

```
✗  waitress 는 이득이 없다
✓  내 클라이언트로는 서버 간 차이를 분해할 수 없다. 08-31 값을 뒤집지 않는다
```

**waitress 가 돌고 있다는 것 자체는 확인됐다** — 기동 로그의 `모드: waitress (스레드 8)`,
설치된 3.0.2, 그리고 `--dev` 를 줬을 때 실제로 다른 모드로 뜨는 것.

> 8081 시험 서버는 **종료했다.** `app`·`tunnel` 두 세션만 남아 있고 배포 주소는 그대로다.

## 5. 「SDK 가 도대체 뭐냐」 — 물어보셔서 적어 둔다

이 저장소가 `SDK` 를 설명 없이 수십 번 쓰고 있다. 답한 내용을 남긴다.

**카카오맵 JavaScript SDK = 카카오가 주는 「지도 그리기 라이브러리 파일」** 이다.
이 앱은 **지도를 직접 그리지 않는다.** `index.html` 이 카카오 서버에서 `sdk.js` 를
받아오고, 그 파일이 타일·핀·확대축소를 전부 한다.

```
브라우저 → dapi.kakao.com/…/sdk.js?appkey=… 요청
         → 카카오가 "이 주소가 등록된 곳이냐" 를 Referer 로 본다
         → 등록됨  : 200 + 라이브러리 → 지도가 뜬다
         → 미등록  : 401           → kakao 객체가 안 생긴다
                                    → js/map.js 의 initMap() 첫 가드에 걸려 오류 화면
```

**그래서 터널 주소가 바뀌면 지도가 죽는다.** 다섯 번째 자리(카카오 콘솔)가 이것이고,
`check.sh` 가 못 보는 유일한 자리다.

`200`/`401` 을 그렇게 반복해서 재는 이유도 여기 있다 — **이 컨테이너에는 브라우저가
안 뜬다**(`libnspr4.so` 없음). SDK 요청 한 번이 브라우저를 대신하는 유일한 확인 수단이다.

## 6. Named Tunnel 기각 — 사용자 판단

> *"네임드 터널로 갈라면 url 사야하니까 힘들고"*

**유료 도메인이 필요하다.** 해커톤 시연용 데모에 그 비용은 맞지 않는다.

이 판단이 중요한 이유는, Named Tunnel 이 **여러 곳에서 「근본 해결」로 권해져 왔다**는
점이다 — §12 재부팅 절 · §12 Kakao API 절 · §13 사용자 판단 대기 표, **세 곳**.
§0 대로 **끝난 판단은 `WORKFLOW.md` 가 가져야** 다음 세션이 또 권하지 않는다.
세 곳 전부 기각으로 맞추고, 뒤집을 조건(운영 전환 · 도메인 확보)까지 적었다.

**그래서 무엇이 남는가** — 재부팅마다 다섯 자리를 다시 맞추는 것을 **받아들이고 간다.**
1~4 는 `url-sync` 가 세어 주므로 실제 위험은 **5번 하나**다. 터널 구조를 못 바꾸는 이상
**5번을 기계로 지키는 것이 남은 유일한 방어**이고, 그 검사는 세 번 제안됐지만 아직 없다.
