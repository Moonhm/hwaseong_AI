- 날짜: 2026-08-26
- 담당: 배포 Claude
- 발단: 사용자 지시 — *"코드 검사하고 최적화 할거 찾아 … 보고하면 내가 개발
  클로드한테 한번더 확인해볼게"*, 이어서 *"3개 전부 진행해 … 확실히 진행하고

- 관련 커밋: `d187304`(사진 재인코딩) · `f7d7e84`(썸네일) · `02aebda`(캐시 헤더)

## 1. 발굴보다 검증이 값을 했다

5축(네트워크·실행·죽은코드·메모리·자산)으로 후보를 뽑고, **제안마다 별도
검증자를 붙여 "실제로 할 가치가 있나"를 따지게** 했다.

결과: **53건 제안 → 22건 채택 / 31건 기각**. 기각률 58%다.

기각 사유의 대부분이 "이론적으로는 맞지만 사용자가 체감하지 않는다" 였다.
죽은 함수 89줄(gzip 0.8KB), 안 쓰는 API 키(111B), 날짜 파싱 중복(97B),
축제 정렬 498→50회(6.8ms) — 전부 숫자로는 개선이지만 3G 환경에서 측정 불가다.

### 검증자가 잡아낸 가장 큰 과장

캐시 헤더 제안이 **"재방문 241KB → 18KB, -92.7%"** 라고 주장했다. 검증해 보니
틀렸다 —

> `no-cache` 는 `no-store` 가 아니다. 브라우저는 본문을 갖고 있고 조건부 GET 을
> 보내 304 를 받는다. 실측한 304 응답 전체 크기 = 300 B(헤더 포함, 본문 0).
> 현재 재방문 전송량은 약 26.5KB 이지 241KB 가 아니다. **약 25배 과장.**

제안자는 자기가 잰 "304 / TTFB 0.5s" 를 적어 놓고도 바이트 절감은 풀 다운로드
기준으로 계산했다. **진짜 이득은 바이트가 아니라 시간**(터널 실측 1.4~1.7초)이었다.

그대로 믿고 "92.7% 절감" 이라고 보고했으면 거짓 성과가 됐다.

## 2. 채택 3건

### ① 사진 141장 재인코딩 — 57.5MB → 20.7MB (64%)

**어제 만든 도구가 아무 일도 안 하고 있었다.** `optimize_images.py` 는
'폭 1200 초과' 와 'PNG' 만 봤는데, places 는 대부분 이미 JPEG 이고 폭이 1200
이하였다. 그래서 "places 전처리 완료(69.1→57.5MB)" 라고 보고했지만 그 감소는
전부 PNG 13장 변환분이었고 **JPEG 은 한 장도 재인코딩되지 않았다.**

실측 bpp(비트/픽셀) 중앙값 2.01 에 최대 14.84 — q99 + 4:4:4 서브샘플링 추정.

**임계 bpp 를 정하지 않았다.** 어떤 값을 잡아도 경계에서 틀린다.
대신 실제로 다시 구워 보고 15% 이상 작아질 때만 교체한다(`MIN_SAVING`).
이미 잘 압축된 파일은 다시 구워도 안 줄어들어 자동으로 건너뛰어진다 —
되돌릴 수 없는 작업이므로 판정을 추측이 아니라 측정에 맡겼다.
346장 중 141장만 대상이 됐다.

### ② 홈 작은 슬롯에 240px 썸네일 — 인기 5장 258KB → 39KB (85%)

38·48·76px 슬롯에 1160x550 원본을 내리고 있었다.
`--thumbs` 로 346장(3.3MB, 평균 10KB)을 굽고 `photoThumb()` 이 `size<=80` 일 때만
쓰게 했다 — 큰 슬롯은 흐려지면 안 된다.

**240px 한 종류인 이유**: 가장 큰 소비처가 `.recent-thumb` 76px 이고 DPR3 에서
228px 를 원한다. 240 이면 38·48·76 을 하나로 덮는다. 160/240 두 종류로 나누면
파일이 두 배인데 절감 차이는 5장에 30KB 뿐이라 관리 비용이 이득을 넘는다.

**무한 루프를 막아야 했다.** 썸네일이 없을 때 원본으로 폴백하는데, `onerror`
안에서 `src` 를 바꾸면 그 실패가 다시 `onerror` 를 부른다. `data-f` 로 재시도
여부를 표시해 한 단계만 내려가게 했다(썸네일 → 원본 → 이모지).

### ③ ?v= 를 단 js/css 만 장기 캐시 — 재방문 재검증 1.4~1.7초 제거

검증자가 붙인 **조건 셋을 전부 지켰다. 하나라도 풀면 되돌릴 수 없다.**

1. **`assets/`·`img/` 는 손대지 않는다.** 이미지 URL 에 `?v=` 가 없고(실측 0건)
   경로가 런타임 조립이라 내용을 갈아도 URL 이 그대로다 — 바로 오늘 places 를
   57.5→20.7MB 로 **같은 이름 그대로** 바꿨다. 장기 캐시였다면 그 이전 방문자를
   되돌릴 방법이 전혀 없었다.
2. **`.json` 에 `immutable` 금지**(3600 만). JSON 버전은 JS 안에 하드코딩이고
   `check.sh` 의 `?v=` 검사는 index.html 의 `.js/.css` 태그만 본다. 갱신하고
   문자열을 안 올리면 아무 검사도 못 잡는데 `immutable` 은 Firefox·Safari 에서
   새로고침조차 무시한다.
3. **로컬 직접 접근은 예외.** 앱의 30개 태그가 항상 `?v=` 를 달아 개발 중
   새로고침이 100% 이 경로를 탄다 — 두 Claude 의 확인 흐름이 막힌다.

## 3. "2번씩 확인하라" 는 지시가 정확한 처방이었다

사용자가 이 세 건을 지시하며 덧붙인 말이다. 오늘 앞서 낸 실패들의 공통 원인이
정확히 **확인 없이 완료 선언** 이었으므로 그대로 따랐다.

| 건 | 검증 1 | 검증 2 |
|---|---|---|
| 사진 재인코딩 | 사전 지문 대조 — 사라짐 0·손상 0·**해상도 변경 0**·안 줄어든 것 0 | 인덱스 재생성 후 실물 없음 0건, 표본 8장 서버 200 |
| 썸네일 | 실서버 표본 10장 전부 200, 413KB→86KB | 렌더러 코드를 재현해 홈 인기 5장 실측 258KB→39KB |
| 캐시 헤더 | 조건별 헤더 **7종 전수** 확인 | 자산 30개 전수 200, ETag 304 정합, check.sh 0 |

**이 세 건에서는 회귀가 하나도 나지 않았다.** 오늘 앞선 작업들과 대조적이다
(로그 `2026-08-26-deploy-full-audit.md` §3 참조 — 캐시 버전 누락·슬래시 미처리·
죽은 FLOOR 셋 다 "확인 없이 완료 선언" 이 원인이었다).

## 4. 보고 수치를 스스로 정정한 것

썸네일 이득을 처음에 "991KB → 75KB" 로 보고했다. 그건 ①번 **이전** 기준이었다.
①로 원본이 이미 줄어 실제 출발점은 258KB 였다. 두 작업의 효과가 겹친다 —
합쳐서 자랑하면 이중 계산이 된다. 커밋 메시지와 사용자 보고 양쪽에 명시했다.

## 6. 남는 것

- `tools/server.py` 는 WORKFLOW §12 상 **개발 Claude 담당**이다. 사용자 지시로
  배포 Claude 가 손댔으니 확인이 필요하다(커밋 메시지에 명시했다).
- 캐시 헤더의 첫 방문자 이득("cf-cache-status DYNAMIC→HIT")은 **검증하지 못했다.**
  trycloudflare Quick Tunnel 은 zone 설정이 없는 무료 제품이라 캐시 규칙 적용이
  보장되지 않는다. 확실한 이득은 재방문 1.4~1.7초뿐이다 — 과장하지 말 것.
- 썸네일은 원본을 교체할 때마다 `--thumbs` 를 다시 돌려야 한다. 지금은 mtime
  비교로 자동 감지하지만, 실행 자체를 잊으면 낡은 썸네일이 남는다.
  사진 반입 절차에 못 박는 편이 좋다.
