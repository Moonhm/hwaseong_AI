### mtime 이 결정적이다

나머지는 "지금 없다" 만 말한다. mtime 은 **"그날 아무 일도 없었다"** 를 말한다.

08-30 에 누가 그 파일을 쓰고 `git checkout tools/server.py` 로 되돌렸다고 해도,
checkout 이 파일을 다시 쓰므로 mtime 은 08-30 이 된다. 08-26 13:30 그대로라는 건
**08-26 커밋 이후로 아무도 이 파일에 쓴 적이 없다**는 뜻이다.

`git log 889bcaf..HEAD` 를 따로 본 이유는 내 쪽 혐의를 지우기 위해서다.
나는 이 세션에서 `git add -A` 를 두 번 썼다. 만약 그 diff 가 작업트리에 있었다면
**내 커밋이 쓸어 담았을 것이다.** 안 담겼다 — 애초에 없었다는 뜻이다.

## 3. 인과도 틀렸다 — 재현으로 확인

> "이 diff 가 남아 있으면 `pull --rebase` 가 막힌다"

`server.py` 와 아무 상관이 없다. **미커밋 변경이 하나라도 있으면 막힌다.**

```bash
$ echo x >> README.md && git pull --rebase
error: 리베이스로 풀하기 할 수 없습니다: 스테이징하지 않은 변경 사항이 있습니다.
error: 커밋하거나 스태시에 넣으십시오.

$ echo x >> README.md && git -c rebase.autoStash=true pull --rebase
이미 업데이트 상태입니다.        # ← 통과한다
```

`README.md` 한 줄이면 똑같이 막힌다. 그러니 **해법은 그 파일을 정리하는 게 아니라
`autostash` 다.** §13 에 적어 뒀다.

그리고 14:10 에 실제로 뭐가 막고 있었는지는 짚인다 — **내 line-ref 작업 11개 파일**이
그때 미커밋 상태였다(`index.html` · `js/map.js` · `tools/check*` 등). 같은 작업트리를
공유하니 배포 Claude 눈에는 "작업트리가 더럽다" 로 보였을 것이다.

## 4. 왜 이게 반복되는가

**같은 날 두 번째다.** 하루 전에는 「메모리 3건이 없더라 → `~/.claude/projects` 는
영속이 아니다」였고(`e8ab243` 로 정정), 이번엔 「작업트리가 더럽다 → `server.py`
미완 diff 때문이다」다. **구조가 같다.**

```
증상을 정확히 관찰한다        ← 여기까지는 맞다
    ↓  (재지 않고 한 칸)
그럴듯한 원인을 고른다
    ↓
문서에 원인으로 박는다        ← 여기서부터 비용이 발생한다
```

두 번 다 **명령 한 줄**이면 갈렸다. `findmnt` 였고, 이번엔 `ls -la` 였다.

비용도 같은 모양이다. 이번 건은 §13 에 **"사용자 판단 대기"** 로 올라갔다.
없는 것에 대해 사용자에게 결정을 요구한 셈이고, 실제로 사용자가 그걸 나에게 전달했다.
셋 중 뭘 골랐어도 **틀린 답**이었다 — "되돌림" 을 골랐다면 멀쩡한 파일에
`git checkout` 을 쳤을 것이다.

§0 에 어제 세운 규칙이 그대로 적용된다 —
**증상에서 원인을 추측했으면, 원인을 직접 재기 전에는 문서에 원인으로 적지 마십시오.**
그리고 여기에 한 가지가 더 붙는다. **인계는 재고 넘기십시오.**
넘기는 순간 상대는 그것을 사실로 놓고 판단한다.
