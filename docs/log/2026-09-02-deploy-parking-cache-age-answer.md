# 「주차장 갱신이 5.8시간째 실패」에 답한다 — 실패한 게 아니라 아무도 안 불렀다

- 담당: 배포 Claude
- 커밋: `PENDING`
- 발단: 개발 Claude 인계 — *"주차장 상류 API 가 5.8시간째 갱신 안 되고 있습니다."*
  사용자 지시 — *"이거 개발 클로드가 작성한건데 철저하게 2번씩 재검토하면서 확인해봐."*

## 0. 결론

**장애가 아니다.** 상류도 서버도 캐시도 정상이다. 세 가지가 갈렸다.

| 인계 내용 | 실측 |
|---|---|
| 상류가 죽었을 수 있다 | **살아 있다.** 200 · 145건 (2회 반복) |
| 개발 컨테이너의 `HTTP 000` | **망 차단이 아니라 TLS.** 배포에서도 똑같이 난다 |
| *"갱신이 계속 실패 중"* | **실패가 아니라 시도가 없었다.** 캐시는 요청이 올 때만 갱신한다 |

**관찰은 전부 정확했다. 틀린 것은 관찰과 결론 사이 한 칸이다.**

## 1. 상류 — 살아 있다 (요청받은 확인 ①)

배포 컨테이너에서 두 곳 다, 2회씩 쳤다.

```
searchParkingList.json   HTTP 200 · 0.124 s
allOperating.json        HTTP 200 · 0.598 s / 0.599 s

원본 145건 · USE_CNT>0 인 곳 112곳
  id541 여울 공원(지하)     총 566 · 사용 338 · 여유 228
  id 19 향남2 하길리        총 346 · 사용 337 · 여유   9
  id 10 수노을 중앙공원     총 325 · 사용 325 · 여유   0   ← 만차
```

## 2. `HTTP 000` 의 정체 — TLS 다. **그리고 이미 문서화돼 있던 것이다**

**배포 컨테이너에서도 `-k` 없이 치면 똑같이 `000 · 0.098초`** 가 난다. 환경 차이가 아니다.

```
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

상류가 **중간 인증서를 안 딸려 보낸다.** `tools/server.py` 가 `verify=False` 를 쓰는 이유가
이것이고, 프록시 경유가 200 인 것도 그래서다.

> **이 사실은 08-31 에 개발 Claude 본인이 실측해 남긴 것이다**
> ([`2026-08-31-dev-brotli-and-api-audit.md`](2026-08-31-dev-brotli-and-api-audit.md) §1) —
> *"상류가 중간 인증서를 안 딸려 보낸다. `verify=False` 로 부르면 `200 · 22,081 B` 가 온다.
> 「개발 컨테이너에서 000」과 「API 가 죽었다」는 다르다."*
>
> **그 로그가 있는데도 같은 `000` 이 다시 올라왔다.** 로그에만 있으면 검색에 안 걸린다는
> §0 의 그 실패이고, 이번엔 그 규칙을 만든 쪽이 밟았다. **`WORKFLOW.md` 로 올렸다.**

## 3. `age` 가 안 줄어든 이유 — 캐시는 **요청이 올 때만** 갱신한다

`tools/server.py` 의 `_upstream()` 은 **요청 처리 경로에서만** 불린다. 배경 타이머가 없고,
프리워밍만 기동 시 `ttl=0` 으로 1회 돈다. 그래서 **트래픽이 없으면 `age` 는 계속 늘어난다.**

### 결정적 실험 — `/healthz` 는 트리거가 아니다

```
A. 요청 전                      realtime age = 21,221.4 s
B. /healthz 를 3번 더 읽는다     realtime age = 21,221.6 s   ← 안 준다
C. /api/parking/realtime 1번     realtime age =      0.7 s   ← X-Cache: fresh
D. /api/parking/list        1번  list     age =      0.2 s
```

**B 가 핵심이다.** 인계는 `/healthz` 를 2분 간격으로 두 번 읽고 *"그 사이 갱신 시도가 한 번도
성공하지 않았다"* 로 읽었는데, **그 사이 시도 자체가 없었다.** `/healthz` 는 상태를 보고만
할 뿐 갱신을 일으키지 않는다. 관찰(`age` 가 경과만큼 늘었다)은 맞고, 그것이 실패의 증거는 아니다.

### 역산하면 마지막 갱신은 내 점검이었다

`age` 21,221초 = **04:31 UTC**. 그 시각에 **배포 Claude 가 점검차 그 API 를 쳤다.**
그 뒤 6시간 동안 아무도 부르지 않았다 — **`age` 가 크다는 것은 「방문자가 없었다」는 뜻**이지
장애 신호가 아니다.

## 4. 「사용자가 5시간 전 숫자를 본다」는 일어나지 않는다

TTL 45초를 넘겨 기다린 뒤 **방문자처럼** 쳤다. 로컬과 **공개 URL 양쪽**에서.

```
x-cache: fresh · x-cache-age: 0.0 · 145건 · 사용중 112곳
```

**TTL 이 지났으면 첫 요청이 상류에서 새로 받는다.** 낡은 값은 상류가 죽었을 때만 나가고,
그때는 `X-Cache: stale` 이 붙는다. 지금 상류는 살아 있다.

> 다만 **인계의 우려 자체는 유효하다.** 상류가 진짜 죽으면 stale 이 나가고, 그때 화면이
> 낡았음을 말하지 않으면 사용자는 그 숫자를 믿는다. 그건 §17 ② 답신에서 개발 Claude 가
> 자기 몫으로 받은 항목이고 그대로 남아 있다. **지금 상황이 그 경우가 아닐 뿐이다.**

## 5. 요청받은 것 — **이미 응답에 실려 있다. 서버 변경 불필요**

*"주차장 API 응답 자체에 캐시 나이나 갱신 시각을 넣어 줄 수 있는지"* 물었는데,
`_serve_upstream()` 이 **모든 응답에 이미 붙이고 있다.**

```
X-Cache: fresh | cache | stale
X-Cache-Age: 0.0
```

**Cloudflare 터널을 통과하는 것까지 확인했다** — 공개 URL 응답 헤더에 그대로 있다.
앱과 같은 오리진이라 `fetch()` 에서 바로 읽힌다.

```js
const r   = await fetch('/api/parking/realtime');
const age = parseFloat(r.headers.get('X-Cache-Age'));
const src = r.headers.get('X-Cache');
```

> `Access-Control-Expose-Headers` 는 없다. 같은 오리진이면 무관하지만 다른 오리진에서
> 시험하면 헤더가 가려진다. **필요하면 말씀해 주시면 한 줄 넣는다** — 지시 없이 안 넣었다.

본문에 넣는 방안도 가능하지만 **헤더가 이미 되는데 스키마를 바꾸면** `js/parking.js` 의
파싱과 `check_data.py` 의 대조를 같이 흔들게 된다. 헤더를 쓰는 편이 싸다.

## 6. 변환은 충실하다 — 시간차와 버그를 갈랐다

같은 순간 대조에서 145건 중 **13건**이 달랐다. 버그로 보일 수 있어 **대조군**을 세웠다.

```
상류 ↔ 상류 (30초 간격)   : 27건 변동 / 145
우리 ↔ 상류 (같은 순간)   : 13건 차이 / 145
```

**상류 자체가 30초에 27건 변한다.** 13건은 두 요청 사이 몇 초의 자연 변동 범위 안이다.
대조군 없이 「13건 불일치」만 봤으면 변환 버그로 보고할 뻔했다.

## 7. 이번에도 내 측정 도구가 틀렸다 — 오늘만 세 번째

앞선 두 건(터널 너머 측정 · `awk` 의 `IGNORECASE`)에 이어 **JSON 파서**가 또 틀렸다.

```
내 파서    d.get('data') 또는 d.get('rows')   → 0건
실제 구조  { "operating": [ … 145건 ] }
```

상류의 최상위 키는 `operating` 이고, 우리 서버 응답은 `{ok, data}` 에 레코드가
`{id, avail, used, open}` 이다. **둘의 키가 서로 다르다.** 추측한 키로 세고 「0건」을
그대로 보고했으면 「상류가 빈 응답을 준다」는 가짜 장애를 하나 더 만들 뻔했다.

> **오늘의 교훈을 한 줄로 줄이면 — 결과가 놀라우면 대상보다 자를 먼저 의심한다.**
> 세 번 다 「서버가 이상하다」로 보이는 결과였고, 세 번 다 자가 틀렸다.

## 8. 어디가 갈렸나 — 절차는 옳았고 한 칸이 비었다

| | 평가 |
|---|---|
| 실측 | **정확하다.** `age` 가 두 번 사이에 경과만큼 늘어난 것은 사실이다 |
| 못 잰 것을 밝힌 것 | **맞게 했다.** `000` 을 단정하지 않고 범위를 적어 넘긴 덕에 TLS 건으로 정확히 잡혔다 |
| 추론 | *"갱신 시도가 한 번도 성공하지 않았다"* — **시도가 실패한 게 아니라 시도가 없었다** |

§0 의 「증상에서 원인을 추측했으면 재기 전에는 원인으로 적지 마십시오」가 걸리는 자리다.
다만 **그 규칙의 후반부(「어디서 쟀는지 적어라」)는 정확히 지켜졌고, 그래서 이 건이
30분 만에 닫혔다.** 범위를 안 적었으면 상류 장애로 오래 갔을 것이다.

> **비용이 어디서 났는지도 적어 둔다.** 이 건은 `WORKFLOW.md` §1 에 **「갱신이 계속 실패
> 중이다」로 현재 사실처럼** 적혀 있었다. §0 의 전제가 「이 파일은 지금 사실을 말한다」이므로
> **틀린 원인이 규칙이 되면 그 뒤로는 아무도 안 잰다.** 그 절을 실측으로 갈아 끼웠다.
