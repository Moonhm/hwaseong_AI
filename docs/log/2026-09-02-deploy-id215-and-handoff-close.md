### `b19` 가 실제로 먹었는지 대조군을 세워 쟀다


**404 만 보고 끝냈으면 「원래 안 붙는 것 아닌가」와 구분이 안 된다.** 200 쪽에 여전히

> 이번 pull 은 새 `<script src>` 가 추가되지 않아 **위험 구간을 우연히 비껴갔다.**

## 6. push 직후 검사가 진짜 사고를 잡았다 — **리베이스가 `?v=` 갱신을 흡수했다**

커밋을 push 하고 나서 `check.sh` 가 **version-guard FAIL** 을 냈다. 오탐이 아니었다.

```
push 직전  git pull --rebase 가 개발 Claude 의 cbbe793 을 끌어왔다
           그쪽도 bump_version.py 를 돌려 ?v= 를 20260826161 로 올려 두었다
           내 커밋의 ?v= 헝크는 '이미 적용됨' 으로 판정돼 리베이스가 떨어뜨렸다
결과       내 커밋에 js/data.js 내용 변경만 남고 index.html 은 빠졌다
           → ?v=20260826161 이 서로 다른 js/data.js 두 벌을 가리킨다
```

**이건 이 저장소가 이미 겪은 사고 모양이다.** 08-31 재독이 세 변종을 적어 뒀는데
(`f7d7e84` 미갱신 · **`a2e84e9` 리베이스 흡수** · `c05d6e9` `--ours` 로 넘김),
그중 두 번째가 그대로 재발했다.

`?v=` 값 자체는 30곳 전부 한 값으로 **일관**돼 있었다. 그래서 `b20`(방금 개발 Claude 가
고친 `?v=` 종류 검사)은 통과한다. **잡은 것은 version-guard 다** — 「js/·css/ 를 고친
최신 커밋이 `index.html` 도 고쳤는가」를 보기 때문이다. 값의 일관성이 아니라
**갱신의 동반 여부**를 보는 검사라서 걸렸다.

> **검사 둘이 서로 다른 축을 본다는 것이 여기서 값을 했다.** `b20` 만 있었으면
> 「1종류로 일관」이라는 초록불을 보고 넘어갔을 자리다.

서버가 `?v=` 를 단 파일을 **1년 `immutable`** 로 내보내므로(§12), 같은 번호에 다른
내용이 한 번 나가면 그 URL 은 강제 새로고침으로도 안 고쳐진다.
`python3 tools/bump_version.py` 로 **`20260826162`** 로 다시 올려 뒤따르는 커밋에 넣었다.

> **왜 안 터졌나** — 실서비스는 이 컨테이너의 디스크를 직접 읽는데, 내 디스크에서는
> 새 `data.js` 와 `?v=161` 이 **함께** 올라갔다. 위험한 것은 `cbbe793` 을 받아 서빙하는
> 쪽이다. 지금은 배포가 한 곳뿐이라 사고로 이어지지 않았을 뿐, **구조는 뚫려 있었다.**
