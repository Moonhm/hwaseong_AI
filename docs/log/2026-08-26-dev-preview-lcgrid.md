# 관광 목록 미리보기 10개 · 지역화폐 레이어 좌표 격자 인덱스

- 날짜: 2026-08-26
- 담당: 개발 Claude (hm8824@naver.com)
- 발단: 사용자 요청 — "아니 왜 이렇게 했어 10개로 해그럼. 그리고 이건 배포 클로드가 준거야
  확인해봐. 4번 지도 지역화폐 레이어가 팬/줌마다 27,374건을 전수 스캔 …
  js/localcurrency.js라 개발 Claude 영역입니다."
- 커밋: `f14bbf0`. 앞 커밋 `be026c0` 을 12분 만에 되짚은 것이 절반이다.

## 1. 미리보기 20 → 10 — 내가 고른 수를 사용자가 되돌렸다

12분 전 `be026c0` 에서 `PREVIEW` 를 20 으로 잡았다. 사용자의 첫마디가
*"아니 왜 이렇게 했어"* 였다.

지금 앱의 미리보기 상수는 셋이다. 값이 다르고, 다른 데는 이유가 있다.

| 목록 | 상수 | 위치 | 값 | 성격 |
|---|---|---|---:|---|
| 소식 탭 카테고리 목록(맛집·주차장·가맹점…) | `LIVING_PREVIEW` | js/living.js:37 | 5 | 확인 |
| 소식 탭 '행사 전체' | `FEST_ALL_PREVIEW` | js/living.js:349 | 5 | 확인 |
| 추천 탭 관광 목록 | `PREVIEW` | js/tourism.js:306 | **10** | 둘러보기 |

(화면 라벨과 `data-page` 가 다르다. `living` = 소식, `tourism` = 추천 —
index.html:679·684 주석 참고)

**5 인 쪽은 '확인' 용이다.** 소식 탭은 목적을 갖고 들어와 맞는지 보고 나간다.
`LIVING_PREVIEW` 를 5 로 둔 이유도 소스에 그대로 있다 — *"94·131·80건을 통째로
쏟으면 아래 목록이 화면을 다 먹는다"*(js/living.js:35-36).
반면 추천 탭 관광 목록은 **'둘러보기'** 용이라 5 면 첫 화면(약 8개 노출,
`be026c0` 390×844 실측)에서 바로 잘려 탐색이 끊긴다.

**그럼 20 은 왜 틀렸나.** `be026c0` 에 내가 쓴 근거는 *"20 이면 2.5화면쯤 훑고
나서 더보기를 만난다"* 였다. 이건 **'더보기를 늦게 만날수록 좋다'** 는 전제 위에
서 있는데, 그 전제가 근거 없이 들어갔다. 더보기는 벌칙이 아니라 이정표다.
10 이면 한 화면을 살짝 넘겨 **스크롤이 막 시작되는 지점**에서 만나므로,
사용자는 "더 있다"는 사실을 스크롤 피로가 쌓이기 전에 안다.

## 2. 숫자로 본 세 선택지

| 미리보기 | 목록 DOM 노드 | 더보기 표시 |
|---|---:|---|
| 없음(관광지 151건 전량) | 2,523 | — |
| 20 | 328 | +131 |
| **10** | **168** | **+141** |

전량·20 은 `be026c0`, 10 은 `f14bbf0` 의 검증값이다(뷰포트를 390×844 로
적어 둔 것은 `be026c0` 쪽뿐이다).
`js/data.js` 를 전수로 세어 카테고리 분포도 다시 확인했다 —
**관광지 151 · 문화재 42 · 축제 50.** 151−10 = 141 로 커밋의 `+141` 과 맞는다.

20 → 10 의 노드 절감(328 → 168)은 그 자체로는 크지 않다. 이 건은 성능이 아니라
**화면 구성** 판단이고, 결정권은 사용자에게 있었다. 내가 20 을 "2.5화면" 이라는
감으로 정한 것이 잘못이었다.

## 3. 지역화폐 레이어 — '한 번' 이 아니라 '계속' 이 문제였다

배포 Claude 가 성능 감사에서 발굴한 ④번 항목이다. 파일이 `js/localcurrency.js`
라 개발 Claude 영역이므로 여기서 구현했다.

`updateLcDisplay()` 는 `onLcMapIdle` 이 80ms 디바운스로 부른다
(js/localcurrency.js:38-43). 그 안에서 레벨 ≤ 5 면 `showViewportMarkers`,
아니면 `showClusters` 로 갈리는데 **둘 다 `lcData` 27,374건을 통째로 훑었다**
(각각 `filter` 와 `forEach`).

한 번 몇 ms 는 아무것도 아니다. 문제는 팬·줌이 연속 동작이라는 것이다 —
지도를 끄는 내내 idle 이 계속 뜨고, 그때마다 27,374번을 돈다.

## 4. 설계 — 좌표 격자 인덱스 (js/localcurrency.js:99-162)

`LC_CELL` = 0.01°(약 1.1km)로 좌표를 잘라 `"y,x"` 문자열을 키로 쓰는 해시
(`_lcGrid`)를 만든다. `_lcBuildGrid()` 가 한 번 만들고, `_lcQuery()` 가
사각 범위와 업종 필터를 받아 후보를 돌려준다.

셀 크기를 정하려고 데이터를 직접 세었다(`js/localcurrency-static.json`).

| 항목 | 값 |
|---|---:|
| 전체 건수 | 27,374 |
| 좌표 없는 건 | 0 |
| 0.01° 셀 개수 | 591 |
| 셀당 평균 | 46.3 |
| 셀당 중앙값 | 6 |
| 가장 큰 셀 | 1,130 |
| 고유 좌표 | 10,755 |

중앙값 6 과 평균 46 이 여덟 배 가까이 벌어진 것이 이 데이터의 성격이다 —
동탄에 몰려 있다. 셀을 더 잘게 쪼개면 순회할 셀이 늘고, 더 키우면 셀 안에서
다시 거르는 비용이 는다. 0.01° 는 그 사이에서 고른 값이다.

**정확성은 셀 크기와 무관하다.** 격자는 후보만 좁히고, 실제 사각 판정과 업종
필터는 `push()` 안에서 다시 한다(:136-140). 그래서 `LC_CELL` 은 성능 상수일 뿐
동작 상수가 아니다 — 나중에 값을 바꿔도 결과가 안 변한다.

**R-tree·quadtree 를 안 쓴 이유.** 데이터가 정적이고(삽입·삭제가 없다), 질의가
항상 축에 나란한 사각형이며, 27,374건은 해시 한 겹으로 충분하다. 무엇보다
이 앱이 부르는 외부 스크립트는 카카오 SDK 하나뿐이다(index.html:938) —
공간 인덱스 라이브러리 하나 때문에 그 상태를 깰 값이 아니다.

`showClusters` 의 `LC_GRID[level]` 과 헷갈리지 않게 주석을 달아 뒀다(:287-288).
그건 **화면에 그릴 뭉치 크기**라 인덱스 셀과 아무 상관이 없다.

## 5. 부팅이 아니라 첫 뷰포트 렌더에서 만든다

구축은 1회 34ms 다(커밋 `f14bbf0` · 소스 주석 :108). 그래서 `_lcQuery` 첫 줄에서
필요할 때 만든다(:133).

```js
if (!_lcGrid || _lcGridN !== lcData.length) _lcBuildGrid();
```

**부팅 구축은 애초에 불가능했다.** `lcData` 는 4.2MB 지연 로드라(js/ui.js:181-201)
부팅 시점에 빈 배열이다. 만들 것이 없다.

그럼 남는 후보는 `_loadLcData` 의 완료 콜백 안에서 만드는 것이었다.
**그것도 버렸다** — `_loadLcData` 를 부르는 곳이 지도만이 아니기 때문이다.
소식 탭 가맹점 목록(js/living.js:91)·홈(js/home.js:987)·반경 500m 찾기
(js/map.js:1064)가 같은 게이트를 쓴다. 지도를 안 켠 사용자에게 34ms 를 물릴
이유가 없다. `_lcQuery` 안의 지연 구축은 **'정말로 격자가 필요해진 순간'** 을
정확히 집는다.

덧붙여 34ms 가 붙는 자리도 나쁘지 않다. 바로 앞에 4.2MB 파싱이 있고, 그건
저사양 기기에서 1초 가까이 메인스레드를 멈춘다(js/ui.js:186-187 주석).
그 뒤의 34ms 는 상대적으로 묻힌다.

## 6. 넓은 뷰포트 폴백 — 이득이 아니라 회귀 방지다

`_lcQuery` 에는 분기가 하나 있다(:147).

```js
var want = (y1 - y0 + 1) * (x1 - x0 + 1);
var keys = Object.keys(_lcGrid);
if (want > keys.length) { /* 존재하는 셀만 순회 */ }
```

왜 필요한지 데이터 bbox 를 재 봤다.

| 항목 | 값 |
|---|---|
| 데이터 bbox | 위도 37.0268~37.2914 · 경도 126.5558~127.1491 |
| bbox 를 0.01° 로 자르면 | 28 × 60 = 1,680 셀 |
| 실제로 값이 있는 셀 | 591 (**35.2%**) |

즉 화성시 전역을 한 화면에 담으면 격자 순회는 1,680칸을 도는데 그중
**1,089칸(65%)이 빈칸**이다. 없는 키를 문자열로 조립해 해시를 두드리는 헛일이
전수 스캔 위에 얹힌다. 그럴 바에는 존재하는 591개 셀만 훑는 게 낫다.

**다만 그래도 결국 27,374건 전부가 `push()` 를 통과한다 — 전수 스캔과 같은 일이
된다.** 그래서 넓은 뷰포트 실측이 **8.92ms → 9.16ms** 다(커밋 `f14bbf0`).
이 분기의 목적은 빨라지는 게 아니라 **느려지지 않는 것**이다.
최적화를 넣으면서 다른 구간을 망가뜨리지 않았다는 증명이 필요했다.

√591 ≈ 24 이므로, 대충 24×24 셀(0.24° 사방)보다 넓어지면 폴백을 탄다.
클러스터 화면(레벨 6 이상)이 이 근처에 걸릴 텐데, **정확히 어느 레벨부터인지는
측정하지 않았다** — 카카오 SDK 는 이 컨테이너에서 뜨지 않는다.

## 7. 실측과 정확성 검증

node 로 이 저장소 데이터를 써서 쟀다. 가운데 줄만 소스 주석(:104)에 남겼고,
나머지 두 줄은 커밋 `f14bbf0` 메시지에만 있다.

| 경우 | 전수 | 격자 | 배율 |
|---|---:|---:|---:|
| 동탄 레벨5 뷰포트(질의만) | 8.13ms | 0.37ms | 22배 |
| **실제 코드 모양(버킷팅 포함)** | **11.5ms** | **3.0ms** | **3.8배** |
| 넓은 뷰포트(폴백 경로) | 8.92ms | 9.16ms | — |

모바일은 3~6배 느리므로 11.5 → 3.0 을 34~69ms → 9~18ms 로 본다(환산이지 실측이 아니다).

전수 스캔과 결과가 **완전히 같은지** 5가지 경우로 대조했고 전부 일치했다.

| 경우 | 건수 |
|---|---:|
| 동탄 레벨5 | 2,896 |
| 제부도 | 64 |
| 도시 전체 | 27,374 |
| 데이터 밖 | 0 |
| 업종 필터(일반음식점+학원) 동탄 / 전체 | 791 / 7,926 |

## 8. 넘겨받은 숫자는 다시 쟀다

배포 Claude 가 준 수치는 **140ms → 33ms** 였는데 내 실측은 **11.5ms → 3.0ms**
였다. 자릿수가 한 자리 다르다. 배율은 4.2배 대 3.8배로 사실상 같아
**개선 방향은 채택하고 절대값만 내 실측으로 갈았다.** 측정 환경 차이로 본다.
(140ms → 33ms 라는 숫자는 배포 로그 어디에도 없다. 내가 커밋 `f14bbf0` 메시지에
받아 적어 둔 것이 유일한 기록이다.)

그냥 받아 적을 뻔했다. 같은 감사의 배포 로그
(`docs/log/2026-08-26-deploy-perf-optimization.md` §1)에서도 가장 크게 틀린 수치는
**넘겨받은 제안에 적혀 있던 숫자**였다 — 캐시 헤더 절감량이 약 25배 과장이었다.
그쪽은 검증해서 걸러 냈고(같은 로그 §4 에는 이미 보고한 뒤 스스로 정정한 건도
따로 있다), 그래서 거짓 성과가 되지 않았다. 넘겨받은 숫자는 반드시 다시 잰다.

## 9. 함께 온 제안 중 하지 않은 것

배포 로그 §5 「하지 않은 것」과 맞춰 봤다. 두 건 다 배포 Claude 자신의 보류
판단이지 나에게 넘긴 숙제가 아니다. 개발 쪽에서 다시 봐도 결론이 같다.

| 항목 | 판단 |
|---|---|
| WebP 전환 | **안 한다.** 추가 이득 14.6% 인데 `<img>` 호출부 21곳에 폴백 분기가 붙는다(배포 Claude 검증). 그 분기가 붙을 자리는 `js/` 안이라 비용은 결국 개발 영역으로 온다. 게다가 `photoThumb()`(js/ui.js:101) 이 `onerror` 로 거는 `_thumbFallback()` 이 이미 **썸네일 → 원본 → 이모지** 2단 폴백이고(js/ui.js:84-88), `onerror` 안에서 `src` 를 갈면 그 실패가 다시 `onerror` 를 부르는 함정 때문에 `data-f` 플래그로 막아 둔 상태다. WebP 를 얹으면 3단이 된다 |
| `restaurants-static.json` 649KB 삭제 | **안 한다.** 지연 로드라 첫 화면 영향이 0 이고, 되살릴 계획이 있는지 확인되지 않았다. 사용자 판단 대기(개발 감사 로그 `2026-08-26-dev-audit-a11y-optimization.md` §7 에도 같은 결론) |

## 10. ⚠ 첫 화면에는 영향이 0 이다

범위를 정확히 적어 둔다. 과장하지 않기 위해서다.

- **부팅·홈 첫 화면: 영향 0.** 그때 `lcData` 는 빈 배열이다.
- **지도 탭에 들어가도 지역화폐 칩을 안 켜면: 영향 0.**
- 칩을 켠 뒤 팬·줌 할 때만 이득이 있고, 그중에서도 **개별 핀 레벨(좁은 화면)**
  에서만 크다. 넓은 화면은 위에 적은 대로 본전이다.

소스에 `⚠` 두 줄(:107·:108)로 못 박아 뒀다. 다음 사람이 이 커밋을
'성능 개선' 으로 뭉뚱그려 인용하지 않게 하기 위해서다.

## 11. 남은 것 (전부 측정하지 않았다)

- `_lcQuery` 는 매 질의마다 `Object.keys(_lcGrid)` 로 591개짜리 배열을 새로 만든다
  (:145). 분기 판정 전이라 빠른 경로에서도 무조건 만든다. 구축 때 개수를 저장해
  두면 없앨 수 있다.
- 폴백 경로(:148-152)는 **셀 단위 사각 판정을 하지 않는다.** 셀의 범위를 먼저 보고
  통째로 건너뛰면 넓은 뷰포트에서도 이득이 날 자리가 있다. 지금은 27,374건 전부가
  `push()` 를 통과한다.
- `_lcGridN` 은 **건수**만 본다(:133). 건수가 같은 채로 내용만 바뀌면 낡은 격자를
  쓴다. 지금 `lcData` 에 대입하는 코드는 js/ui.js:190 한 곳뿐이라 실제로 재구축이
  일어나는 경로는 없다 — 앞으로를 위한 안전장치에 가깝다.
- 좌표가 아닌 질의는 격자로 못 줄인다. 홈 검색은 이름·업종 문자열 매치라
  매치가 5건에 못 미치면 27,374건을 다 돈다(js/home.js:502-507, 소스 주석에 이미
  명시돼 있다). 반경 500m 찾기(js/map.js:1067)도 전수지만 사용자가 한 번 누를 때
  한 번이라 idle 반복과 성격이 다르다. 둘 다 이번에 손대지 않았다.
  (소식 탭 가맹점 목록은 앞에서 80건만 잘라 쓰므로 전수 스캔이 아니다 —
  js/living.js:110-114)
