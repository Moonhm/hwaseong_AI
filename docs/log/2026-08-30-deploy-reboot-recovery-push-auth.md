## 3. 진짜 발견 — pull 은 되는데 push 만 죽어 있었다

사용자가 "깃은 연결되어 있니" 라고 물은 것이 계기였다. `git ls-remote` 가 정상 응답해서
"연결됨" 으로 보고할 뻔했는데, `git push --dry-run` 을 마저 돌려 보니:

```
fatal: could not read Username for 'https://github.com'
```

**공개 저장소는 읽기가 무인증이다.** 인증이 통째로 죽어도 fetch · pull · ls-remote 는
전부 통과한다. 읽기만 확인하고 "깃 정상" 으로 보고했다면, 작업을 다 끝내고
push 하는 순간에야 발견했을 것이다.

인증이 살던 곳이 전부 영속 영역(`/home/jovyan/work`) 밖이었다.

| 증발한 것 | 있던 곳 |
|---|---|
| gh CLI 인증 | `~/.config/gh/hosts.yml` |
| git credential 저장 | `~/.git-credentials` — 파일 자체가 없어짐 |
| git 전역 설정 | `~/.gitconfig` — 빈 것 확인 |
| pip 설치분 (flask · requests) | conda site-packages |

repo 로컬 설정(`user.email` 등)은 `.git/config` 가 work 안이라 살아남았다.

복구는 사용자가 했다 — `gh auth login`(브라우저 기기 인증) → `gh auth setup-git`.
브라우저 인증이라 **이 단계는 항상 사용자 몫이다.** 재인증 뒤 `git push --dry-run` 이
`Everything up-to-date` 로 통과하는 것을 확인했다.

토큰을 work 안이나 저장소로 옮기면 영속은 되지만 **공개 저장소라 하지 않는다.**
재부팅마다 사용자가 한 번 로그인하는 것이 맞는 비용이다.

## 4. 교훈은 로그가 아니라 체크리스트에 넣었다

이 복구 절차를 이 로그에만 적으면, 로그에만 적힌 인계가 실종된 `js/weather.js` 건

그래서 **§12 에 「컨테이너가 재부팅됐다면」 절을 신설**해 절차를 그쪽에 두고,
이 로그에는 경위만 남긴다. 로그는 "그때 무슨 일이 있었나", `WORKFLOW.md` 는
"지금 무엇이 참인가" — §0 의 구분 그대로다.

## 6. 세 번째 재부팅 (14:05) — 대비해 둔 메모리가 같이 사라졌다

2·3·4절을 다 쓰고 **커밋하지 않은 채** 서비스 재기동 지시를 기다리던 중 다시 끊겼다.
사용자 지시는 *"또 서버가 상태가 안좋아서 재부팅 될수있으니까 일단 진행상황 메모리에
기록해놔"* 였는데, 확인해 보니 **그 메모리가 이번에 사라진 것**이었다.

08:20 경 이 세션은 재부팅에 대비해 Claude 메모리 3건을 남겼다. 14:05 재부팅 뒤
`~/.claude/projects/-home-jovyan-work/memory/` 는 **빈 디렉터리**였다 (디렉터리 자체가
14:06 에 새로 만들어져 있었다). `mount` 로 이유가 확인됐다.

```
/dev/sdb1 on /home/jovyan/work                       ext4 (rw)   ← 저장소
/dev/sdb1 on /home/jovyan/shared                     ext4 (ro)
/dev/sdb1 on /home/jovyan/.claude.json               ext4 (rw)   ← 파일 하나
/dev/sdb1 on /home/jovyan/.claude/.credentials.json  ext4 (rw)   ← 파일 하나
overlay    on /                                      ← 나머지 전부
```

영속은 **이 네 경로뿐**이다. `~/.claude/` 는 통째로 영속인 게 아니라 그 안의
**파일 두 개만** 따로 마운트돼 있다. 메모리·세션 기록이 들어가는 `~/.claude/projects/` 는
그 밖이라 매번 지워진다. Claude Code 로그인이 재부팅을 넘겨 유지되는 것도 같은 이유다 —
`.credentials.json` 이 마운트된 파일 둘 중 하나다. **로그인은 남고 기억은 안 남는다.**

그래서 §12 「컨테이너가 재부팅됐다면」에 이 마운트 표와
**「Claude 메모리는 인계 수단이 아니다」** 항을 넣었다. 4절에서 "로그에만 적으면
실종된다" 며 §12 로 옮긴 것과 같은 이유이고, 한 칸 더 나간 것이다 — **메모리에만
적으면 그건 실종이 아니라 소멸이다.**

살아남은 것과 사라진 것을 갈라 보면 기준이 분명하다.

| 08:24 이후 상태 | 14:06 확인 결과 |
|---|---|
| `WORKFLOW.md` 수정 · 이 로그 파일 | ✅ 그대로 (work 안) — 커밋 전이었는데도 살았다 |
| 메모리 3건 | ❌ 소멸 |
| gh 인증 (사용자가 08:1x 에 재로그인) | ❌ 또 소멸 — push 다시 막힘 |
| flask·waitress | ❌ 여전히 없음 (애초에 설치 전이었다) |
| 로컬·원격 커밋 `889bcaf` | ✅ 일치, 유실 0 |

`git pull` 결과 **개발 Claude 가 올린 새 커밋은 아직 없다.** 서비스 재기동은 5절 그대로
대기 상태를 유지한다.

이번엔 세 번째를 겪고 나서야 **커밋을 먼저** 한다. 위 표에서 보듯 work 안의 파일은
커밋 없이도 재부팅을 넘겼지만, 그건 이 컨테이너가 살아 있을 때 이야기다 —
컨테이너가 갈리면 push 된 것만 남는다.
