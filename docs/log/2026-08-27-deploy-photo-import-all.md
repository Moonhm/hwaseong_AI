## 1. 첫 시도에서 33장 중 5장만 처리했다

`find` 로 폴더를 훑었는데 확장자 목록이 이랬다.

```
-iname "*.jpg" -o "*.jpeg" -o "*.png" -o "*.webp" -o "*.heic" -o "*.gif"
```

**`.jfif` 가 없다.** 올라온 33장 중 28장이 `.jfif` 였으므로 그 28장을 통째로
못 봤고, 5장만 처리해 놓고 "사진 없는 곳 33 → 28곳" 이라고 보고했다.

`.jfif` 는 JPEG File Interchange Format 이다 — **내용은 그냥 JPEG 이고**
윈도우 크롬에서 이미지를 저장하면 흔히 붙는다. 나는 그것을 '사진이 아닌 것'
으로 걸러 낸 셈이다.

사용자 지적: *"야 뭔소리야 jfif 이 확장자도 다 사진이야"*

그대로 넣으면 **조용히 안 뜬다.** 나는 이걸 눈으로 보고 손으로 고쳤다.

사용자 지적: *"저건 그냥 오타수준이잖아 저런것도 안하는게 어딨어"*

맞는 말이다. 사람이 매번 눈으로 잡을 수는 없고, 잡는다는 전제 자체가 틀렸다.

## 3. 둘 다 '사람이 목록을 관리하는' 방식이라 도구로 옮겼다

`tools/import_photos.py` 신설.

| 무엇 | 어떻게 |
|---|---|
| 확장자 | `.jpg .jpeg .jfif .jpe .png .webp .gif .bmp .avif` 를 전부 읽는다. 내용이 JPEG 인 것(`.jfif .jpe .jpeg`)은 `.jpg` 로 통일해 반입 |
| 이름 | 정확 일치 → 그대로 / **공백·대소문자만 다름 → 정확명으로 자동 교정** / 그 외 → 반입하지 않고 목록으로 보고(임의 추측 금지) |
| 정규화 | NFC + 확장자 소문자 |
| 원본 | 건드리지 않는다 |

`tools/optimize_images.py` · `tools/build_photo_index.py` 의 `EXTS` 에도 `.jfif` 를
넣었다. **빠뜨리면 인덱스가 그 파일을 아예 못 본다** — 도구를 하나만 고치면
같은 사고가 다른 자리에서 난다.

`WORKFLOW.md` '장소 사진' 절도 고쳤다(사용자 지시). 반입은 반드시 도구로 하라는
명령과 위 두 사고를 표로 남겼다. **새 확장자를 만나면 파일을 옮기지 말고
`IMG_EXTS` 에 추가하라**고 적었다.

## 5. 재확인에서 또 하나 나왔다 — 확장자 다른 중복

사용자가 *"다시 한번 확인하고 정리해"* 라고 해서 다시 셌더니
`places 380장 / thumbs 379장` 으로 1장이 어긋나 있었다.

```
새싹동산 청려수련원.jpg   46KB
새싹동산 청려수련원.png  625KB   ← 같은 장소가 두 벌
```

경위가 이렇다:

1. 1차 반입에서 `.png` 를 넣었고 `optimize_images` 가 `.jpg` 로 바꾸며 `.png` 를 지웠다
2. 2차 반입에서 `import_photos` 가 **`out.exists()` 만 봤다.** `.jpg` 는 있지만
   `.png` 는 없으니 "없다" 고 판단해 원본 `.png` 를 다시 복사했다
3. 그 뒤 `optimize_images` 는 대상(`.jpg`)이 이미 있어 변환을 건너뛰었다 —
   **내가 넣어 둔 데이터 소실 방지 가드가 작동한 것이다**
4. 결과가 두 벌이고 인덱스에도 2장으로 잡혔다

가드는 제 일을 했다. 서로 다른 사진이 덮여 사라지는 것은 막았다.
문제는 그 앞단이라 `import_photos` 를 고쳤다 —
`out.exists()` → `DST.glob(target + ".*")`. 확장자와 무관하게 그 장소 파일이
이미 있으면 복사하지 않는다.

중복 제거는 `.jpg` 가 정상 이미지인지 `verify()` 한 뒤에만 나머지를 지우도록 했다.

> **이건 검증을 두 번 하지 않았으면 못 찾았다.** 첫 검증(파일·인덱스 정합)에서
> 전부 OK 가 떴는데, 파일 수를 세는 줄에서만 380 vs 379 가 보였다.
