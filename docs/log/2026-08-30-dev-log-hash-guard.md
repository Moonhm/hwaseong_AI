# 로그가 가리키는 커밋이 저장소에 없었다 — log-hash 검사 신설

- 날짜: 2026-08-30
- 담당: 개발 Claude (hm8824@naver.com)
- 커밋: `(뒤따르는 커밋에서 채운다 — 아래 3절의 이유로 amend 하지 않는다)`
- 발단: 서버가 재부팅되어 중단된 작업을 복원하던 중, `docs/log` 두 건이 적어 둔
  커밋 해시가 **이 저장소에 도달할 수 없는 해시**임을 발견했다.

---

## 1. 무엇이 틀렸나

| 로그 | 적혀 있던 해시 | 실제 |
|---|---|---|
| `2026-08-29-dev-unified-search.md` | `103dcdc` | `62d9fe9` |
| `2026-08-29-dev-tide-midnight-crossing.md` | `c1ec97a` | `fe4ec70` |

머리줄에 `- 커밋:` 이 있는 로그 7개 중 **2개**가 틀렸다. 나머지 5개(해시 9개)는
전부 정상이다.

하필 **규칙을 만든 그날 쓴 두 건**이 틀렸다. `20366e7`(2026-08-29 12:11)이
"로그 머리에 커밋 해시를 적으라"를 §0 에 넣었고, 그 뒤에 쓴 로그가 정확히 두 개인데
**둘 다** 틀렸다. 규칙 준수율 100%, 정확도 0%다.

## 2. 왜 그렇게 됐나

절차가 이랬다.

```
① git commit                → 해시 103dcdc 가 나온다
② 그 해시를 로그 머리에 적는다
③ git commit --amend        → ②를 커밋에 포함시킨다. 해시가 62d9fe9 로 바뀐다
```

**③ 이 ②를 무효화한다.** 자기 자신의 해시를 자기 안에 적으려는 순간 생기는 순환이고,
amend 를 몇 번 반복해도 수렴하지 않는다. 매번 새 해시가 나온다.

`20366e7` 은 "해시를 적어라"까지만 정하고 **언제 적을지**를 정하지 않았다.
그 빈칸을 절차가 제일 자연스러운 순서(커밋 → 해시 확인 → 적기 → amend)로 메웠는데
그 순서가 틀린 순서였다.

## 3. 왜 사람 눈으로는 안 걸리나

세 가지가 겹쳤다.

**(1) 버려진 해시는 로컬에만 있다.** `103dcdc` 도 `c1ec97a` 도 이 워킹트리에서는
`git show` 가 멀쩡히 내용을 보여준다 — `reflog` 가 붙들고 있기 때문이다. 그런데
push 도 clone 도 도달 불가능한 객체는 나르지 않는다. **저장소를 받은 사람에게는
없는 해시다.** `git gc` 가 한 번 돌면 이 컴퓨터에서도 사라진다.
즉 **틀렸다는 사실이 틀린 곳에서는 안 보이고, 안 보이는 곳에서만 보인다.**

**(2) 7자리 16진수는 다 똑같이 생겼다.** `103dcdc` 와 `62d9fe9` 를 나란히 놓아도
어느 쪽이 맞는지 알 방법이 사람에게는 없다. 검토로 걸러질 종류의 오류가 아니다.

**(3) 규칙만 있고 검사가 없었다.** `check.sh` 는 데이터·마크업·JS·캐시·자산을 보는데
`docs/log` 는 아무도 안 봤다. §0 이 세운 목적이 "**기계로** 확인할 수 있어야 한다"인데
정작 그 기계가 없었다.

## 4. 고친 것

**(a) 두 파일의 해시를 정정했다.** `docs/log` 는 §0 이 "기존 파일은 고치지 않는다"로
못박은 영역이지만, 이건 기록을 덧쓰는 것이 아니라 **틀린 사실을 바로잡는 것**이다.
가리키는 커밋이 없는 해시는 §0 이 세운 목적 자체를 무너뜨린다. 그 예외를 §0 에
명시했으니 다음 사람이 고쳐도 되는지 망설이지 않아도 된다.

**(b) `tools/check.sh` 에 log-hash 검사를 넣었다.** `docs/log/*.md` 의 `^- 커밋:`
머리줄에서 백틱 안 해시를 전부 뽑아 두 가지를 본다.

| 잡는 것 | 판정 |
|---|---|
| 저장소에 없는 객체 | `git cat-file -e <h>^{commit}` 실패 → FAIL |
| 있지만 `HEAD` 에서 도달 못 함 | `git merge-base --is-ancestor` 실패 → FAIL |

두 번째가 이번 사고다. FAIL 은 파일:줄, 그 커밋의 제목, 살아 있는 쪽을 찾는 명령까지
찍는다 — 해시만 보여 주면 사람이 할 수 있는 게 없기 때문이다.

**(c) `WORKFLOW.md` §0 에 함정과 절차를 적었다.** "amend 를 했으면 해시를 다시 읽어
고치고 그 수정은 **뒤따르는 커밋**에 넣어라" 또는 "amend 할 생각이면 해시를 나중에
적어라". 이 문서 머리줄이 비어 있는 것이 그 규칙을 따른 결과다.

## 5. 검사가 실제로 잡는지 — 양방향으로 확인했다

통과만 확인하는 것은 확인이 아니다. 일부러 깨뜨려 봤다.

| | 넣은 값 | 결과 |
|---|---|---|
| 지금 상태 | `62d9fe9` | 통과, exit 0 — "해시 11개 전부 살아 있다" |
| A. amend 로 버려진 해시 | `103dcdc` | **FAIL**, exit 1, 파일:줄 + 커밋 제목 출력 |
| B. 없는 해시 | `deadbee` | **FAIL**, "이 저장소에 없는 커밋이다" |
| 되돌린 뒤 | `62d9fe9` | 통과, exit 0 |

A 가 핵심이다. `103dcdc` 는 `git show` 로 내용이 보이는 해시라서 **존재 검사만으로는
통과한다.** 도달 가능성까지 봐야 잡힌다.

## 6. 안 한 것

- **머리줄 없는 로그 60개를 FAIL 로 만들지 않았다.** `20366e7` 이 "기존 60여 개에
  소급 적용하지 않는다"를 명시했고, 배포 Claude 문서까지 건드리면 충돌 지점이 된다.
  상시 빨간불인 검사는 곧 무시되거나 지워진다(check.sh 설계 원칙 3). 대신 `7/67` 을
  정보 줄로 찍어 현황이 보이게만 했다.
- **pre-commit 훅으로 만들지 않았다.** 이 저장소엔 훅이 없고 `check.sh` 가 유일한
  관문이다. 훅은 clone 하면 안 따라와서 배포 Claude 쪽에서 조용히 빠진다.
- **로그가 없는 커밋을 찾아 주지는 않는다.** §0 이 원한 커버리지 확인의 나머지 절반인데,
  "로그 파일을 만들 만한 커밋"의 기준이 사람 판단(§0 의 「왜가 궁금할 것인가」)이라
  기계가 정할 수 없다. 이번 검사는 **적혀 있는 해시가 맞는가**만 본다.
