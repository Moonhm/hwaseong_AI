## 1. 하루 만에 규칙이 바뀌었다 — immutable 이 켜진 순간

배포 Claude 가 `02aebda`(13:25:20)에서 `tools/server.py` 에 캐시 헤더를 넣었다.
핵심은 `_cache_headers`(server.py 171행)의 여덟 줄이다.

```python
if not request.args.get("v"):
    return resp                      # 버전이 없으면 무효화 수단이 없다
p = request.path.lstrip("/")
if p.startswith(("js/", "css/")):
    if p.endswith((".js", ".css")):
        resp.headers["Cache-Control"] = "public, max-age=31536000, immutable"
    elif p.endswith(".json"):
        resp.headers["Cache-Control"] = "public, max-age=3600"
```

`?v=` 를 단 `js/`·`css/` 아래 `.js`/`.css` **만** 1년 immutable 이다. 그 앞에
로컬 호스트 예외가 있고, `assets/`·`img/` 는 아예 손대지 않는다.

이 커밋이 규칙을 바꿨다. 어제까지는 `?v=` 를 안 올려도 Flask 기본값인 no-cache 덕에
조용히 넘어갔다. 이제는 **같은 `?v=` 번호로 내용이 다른 파일을 한 번 내보내면
그 URL 이 굳는다.** 이미 받아 간 브라우저는 다시 묻지 않는다.
서버 주석은 `immutable` 을 Firefox·Safari 가 강제 새로고침으로도 무시하지
못한다고 적어 놓았다.

이 저장소에서 이게 특히 무서운 이유가 하나 더 있다. `tools/check.sh` 머리말에
적혀 있듯 **빌드도 배포 절차도 없고 push 가 곧 실서비스**다. 보통 버그는 다시
푸시하면 그 순간 고쳐진다. 이건 아니다. 잘못 나간 바이트가 사용자 기기 안에
남고, 서버를 아무리 고쳐도 그 사본에는 손이 닿지 않는다.

### 다만 '영영 못 고친다' 는 과장이다 — 정확히 말해 둔다

`index.html` 은 `?v=` 없이 `/` 로 요청되므로 위 함수의 첫 줄에서 그대로 빠져나가
no-cache 로 남는다. 그래서 `?v=` 를 올리면 **URL 자체가 새것**이 되고 그 순간
전원이 복구된다. 굳는 것은 '이미 나간 그 번호' 이고, 진짜 위험은
**아무도 눈치채지 못해 번호를 영영 안 올리는 경우**다.

진짜로 손쓸 수 없는 쪽은 따로 있다. 사진이다. `assets/`·`img/` 는 URL 에 `?v=` 가
없고 경로가 런타임 조립(`placePhotoSrc`)이라 내용을 갈아도 URL 이 그대로다 —
새 URL 을 만들 방법 자체가 없다. 그래서 `server.py` 는 그쪽을 건드리지 않았다.
같은 날 사진을 57.5MB → 20.7MB 로 **같은 이름 그대로** 다시 구웠으니 실제로
아슬아슬했다. 다만 `assets/` 는 `.gitignore` 라 추적 파일이 0건이고, 그 작업의
커밋(`d187304`)에 들어 있는 것은 `tools/optimize_images.py` 한 개뿐이다 —
용량 수치는 그 커밋 메시지와 `server.py` 주석의 자기 보고이고 나는 다시 재지 않았다.

## 3. version-guard — '작업트리' 가 아니라 '커밋 이력' 을 본다

### 왜 기존 검사가 못 잡았나

`tools/check.sh` 에는 이미 `precommit_guard` 가 있었다. 그런데 두 군데가 비었다.

1. `git status --porcelain -- js/` — **작업트리**만 본다. 커밋을 나눠 하면
   커밋 시점의 작업트리가 깨끗해 그대로 통과한다.
2. `--precommit` 을 붙여야만 도는 **선택 항목**이었다.

게다가 (b)절의 날짜 비교는 주석이 스스로 밝히듯 "같은 날 두 번째 수정은 못 잡는다".
`?v=` 가 `20260826NNN` 꼴이라 날짜 단위 비교로는 하루에 열 번 고치는 날을 못 덮는다.

### 실제 구현 (check.sh 166~181행, 29줄 추가)

```bash
c=$(git log -1 --format=%H -- js/ css/ 2>/dev/null)
[ -z "$c" ] && { echo "  i     js/·css/ 커밋 이력이 없다"; return 0; }
files=$(git show --name-only --format="" "$c" 2>/dev/null)
if echo "$files" | grep -qx "index.html"; then ... return 0; fi
echo "  FAIL  js/ 또는 css/ 를 고친 최신 커밋이 index.html 을 안 고쳤다 — ?v= 가 안 올랐다"
```

`js/` 또는 `css/` 를 건드린 **가장 최근 커밋 한 건**을 찾아, 그 커밋의 변경 파일
목록에 `index.html` 이 정확히(`grep -qx`) 들어 있는지만 본다. 없으면 FAIL 이고
해당 커밋 해시·제목·변경 파일을 전부 찍는다.

검증은 실패 주입으로 했다 — 이 커밋 직전 상태에서 돌리니 `f7d7e84` 를 정확히
지목하며 FAIL, `?v=` 를 올려 커밋한 뒤에는 통과했다.

**`--precommit` 이 아니라 기본 검사로 넣었다.** immutable 이 켜지기 전에는 이 규율을
어겨도 no-cache 가 덮어 줬다. 이제는 아니다. 선택 항목으로 두면 안 붙이고 돌린 날은
검사가 없는 것과 같다. `precommit_guard` 는 지우지 않고 그대로 뒀다 — 커밋 **전에**
잡는 유일한 검사라 역할이 겹치지 않는다.

## 5. 병행 세션이 같은 번호에 도달하는 구조적 문제

`WORKFLOW.md` 에 이미 규칙이 있다.

> | `index.html` 의 `?v=` 값 | **큰 숫자를 채택한다.** 기계적으로 결정되므로 고민하지 말 것 |

이 규칙은 **두 값이 다를 때만** 작동한다. 두 세션이 각자 '현재 값 + 1' 을 계산하면
같은 값에 도달하고, 그러면 고를 큰 숫자가 없다. 더 나쁜 것은 그때 충돌조차 안 난다는
점이다 — 값이 같으면 git 이 갈등을 보여 주지 않고 그냥 한쪽을 삼킨다.
**충돌은 눈에 보이지만 흡수는 안 보인다.** 이번에 내가 당한 게 그것이다.

이 날 세 번째 사례도 있었다. 15:00 의 `c05d6e9`(배포)가 `js/map.js`·`js/data.js`·
`css/20-map.css` 를 고치고 `index.html` 을 아예 안 건드린 채 나갔고,
`a6c277e`(15:01)가 135 → 136 으로 복구했다. 그쪽 원인은 리베이스 충돌을 `git checkout --ours index.html` 로 넘긴 것이다 —
어느 쪽을 고르든 '내 변경이 반영된 버전' 이 아니다.

지금 방식은 **사후 대응**이다. 부딪히면 번호를 더 올려 회피한다. 한계를 솔직히 적는다.

| 한계 | 내용 |
|---|---|
| 번호가 내용과 무관 | `?v=` 는 그냥 증가하는 정수다. 내용이 같아도 다르게, 달라도 같게 만들 수 있다. 내용 해시라면 구조적으로 안 겹치지만 이 저장소에는 빌드 도구가 없다 |
| 사후 검사 | version-guard 는 **커밋 이력**을 본다. 나쁜 커밋이 만들어지는 것 자체를 막지 못하고, 만들어진 뒤에 알려 준다 |
| 최근 한 건만 본다 | `git log -1 -- js/ css/` 다. 빠뜨린 커밋 위에 제대로 된 커밋을 하나 더 쌓으면 앞의 누락은 영영 안 보인다 |
| 값은 안 본다 | `index.html` 이 변경 목록에 **있기만** 하면 통과다. 마크업만 고치고 `?v=` 를 안 올려도 잡히지 않는다 |
| JSON 은 밖에 있다 | `DL_VER` 등 JS 안에 하드코딩된 캐시 버스팅은 이 검사 밖이다. `server.py` 가 `.json` 에 immutable 을 안 붙인 이유가 정확히 이것이다 |

`WORKFLOW.md` 에는 아직 `version-guard`·`bump_version.py`·`immutable` 이라는 말이
한 번도 안 나온다(문자열 검색 0건). 규칙이 `tools/` 소스 주석과 커밋 메시지에만
있다. 문서 반영은 남은 숙제다.

## 6. bump_version.py 에 DL_VER 동기화를 더했다

`tools/bump_version.py` 는 배포 Claude 가 만든 도구다. 자기 sed 사고의 근본 원인을
없앤 것이다 — **다음 값을 사람이 적지 않고 현재 값을 읽어 올린다.**
쓴 뒤 다시 읽어 전부 같은 값이 됐는지 확인하고, 아니면 종료 코드 1 을 낸다.

여기에 `js/datalab.js` 의 `DL_VER` 동기화를 더했다(`DL_TARGET`/`DL_PAT`).
필요했던 이유는 소스에 있다.

```js
var DL_VER   = '20260826138';
...
fetch('js/' + file + '?v=' + DL_VER)
```

데이터랩은 자기 데이터 파일을 `index.html` 과 **별개인** `DL_VER` 로 캐시버스팅한다.
대상은 `datalab_naviranking_hwaseong_2026.json`(36KB) ·
`datalab_tourism_stats.json`(491KB) · `citytour_courses_hwaseong.json`(12KB) 3개이고,
`dlLoad()` 가 화면에서 부르는 지점이 9곳이다. 이 값은 지금까지 **손으로** 맞춰 왔다 —
`f14bbf0`·`6836bcb`·`a2e84e9` 에서 내가 직접 한 줄씩 고쳤다(세 커밋 다 통계가
`js/datalab.js | 2 +-` 다). 한쪽만 올리면 JSON 이 낡은 채로 남는다. `server.py` 가 `.json` 에는 immutable 대신 1시간만 주므로 `js`/`css` 만큼
위험하지는 않지만, **손으로 맞추는 값을 남겨 두면 언젠가 또 어긋난다.**

`DL_PAT` 이 1곳을 못 찾으면 조용히 넘어가지 않고 경고를 찍는다. 0곳이면 변수명이
바뀐 것이고 2곳이면 복사본이 생긴 것이라, 어느 쪽이든 사람이 봐야 한다.
검증: 126 → 128 로 `index.html` 30곳과 `DL_VER` 가 함께 올라갔다.

이 도구가 생긴 뒤로 `?v=` 를 손으로 올리지 않는다. 내 sed 방식도 같은 사고를 낼 수
있었고, 실제로 리베이스로 한 번 냈다.

## 7. check.sh 는 종료 코드로 판정한다

이번 두 사고가 다 `check.sh` 가 잡았다고 쓸 수 있는 것은 **종료 코드를 봤기 때문**이다.
`WORKFLOW.md` 의 규칙을 그대로 옮긴다.

> | **`check.sh` 는 종료 코드로 판정** | `bash tools/check.sh; echo $?` 로 볼 것.
> `grep "── FAIL"` 로 축별 합계만 보면 **실패를 놓친다** — 실제로 2026-08-26 에 데이터 축이
> `FAIL 7` 인 채로 며칠 갔는데 다른 축의 `── FAIL 0` 두 개만 보고 통과로 보고했다.
> grep 은 '무엇이 실패했는지' 볼 때만 쓴다 |

`check.sh` 는 설계상 `&&` 로 잇지 않고 전부 돌린 뒤 끝에 모아 보고한다. 그래서 출력
중간에 `FAIL 0` 이 여러 줄 보인다 — 그 중 하나만 grep 으로 집으면 통과처럼 읽힌다.
내가 그렇게 잘못 보고한 적이 있어 이 규칙이 문서에 박혔다.

종료 코드를 봐도 부족한 경우가 하나 더 있다. `a6c277e` 의 기록에 따르면 배포 Claude 는
check 와 push 를 **같은 명령줄에 이어 붙여** 두어, 실패를 보고도 이미 나간 뒤였다.
검사는 push 앞에서 **끊어져야** 의미가 있다.

## 8. 안 한 것과 그 이유

| 안 한 것 | 이유 |
|---|---|
| `precommit_guard` 를 고쳐 쓰기 | 작업트리 기반이라 커밋을 나누면 구조적으로 못 잡는다. 고치는 대신 이력 기반 검사를 **따로** 만들고 둘 다 남겼다 |
| version-guard 를 `--precommit` 에 넣기 | 안 붙이고 돌린 날은 검사가 없는 것과 같다. immutable 이 켜진 이상 그 하루가 치명적이다 |
| `.json` 에 immutable | JSON 버전은 JS 안에 하드코딩이라 `check.sh` 의 어떤 검사도 못 본다. 못 잡는 것에 되돌릴 수 없는 헤더를 붙일 수는 없다 |
| `assets/`·`img/` 에 캐시 헤더 | URL 에 `?v=` 가 없고 경로가 런타임 조립이라 새 URL 을 만들 수단이 없다 |
| `index.html` 에 캐시 헤더 | 그게 캐시되면 `?v=` 갱신이 영영 전달되지 않는다 — 유일한 탈출구를 막는 셈이다 |
| sed 로 `?v=` 올리기 | 찾는 문자열이 없으면 0건 치환하고 **성공으로 끝난다**. 사고의 근본 원인이었다 |
