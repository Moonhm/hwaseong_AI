## 경량화 — 방식을 두 번 바꿨습니다

사용자 지시는 "용량 큰 원본은 전부 읽고 재편성해 최소화한 뒤 원본 삭제" 였습니다.

**1차 시도(실패)** — 행마다 `{"짧은키":"값"}` 으로 다시 쓰기.
6만 행 7컬럼 CSV **5.3MB → 7.7MB 로 오히려 커졌습니다.** 키가 42만 번 반복되기 때문입니다.
그런데 코드는 `(1 - nb/size) * 100` 을 그대로 찍어 **"-45% 감소"** 라는 말이 안 되는 문구를 출력했고,
그 상태로 **원본을 지웠습니다.** 시험이 아니라 실제 데이터였으면 손실이었습니다.

**2차(채택)** — columnar. 열 이름을 한 번만 적고 행은 값 배열로.

```json
{"cols":["가맹점명","업종","주소"],"n":60000,"rows":[["가게0","일반음식점","..."], ...]}
```

**5.3MB → 331KB (94% 감소).**

**안전장치** — 결과가 원본보다 크면 gzip 하고, 그것마저 크면 **경량화를 포기하고 원본을 남깁니다.**
"경량화했다"면서 용량이 늘고 원본까지 지우는 것이 가장 나쁜 결과입니다.

## `data/` 구조

| 경로 | 내용 | git |
|------|------|-----|
| `data/raw/` | 원본 보관 | 제외 (`.gitignore`) |
| `data/processed/` | 재편성·경량화한 실사용 파일 | 추적 |
| `data/descriptions/` | 웹사이트 설명문 — 나중에 앱 화면에 넣을 것 | 추적 |
| `data/sources/` | 출처 URL·API 명세 | 추적 |
| `data/CATALOG.md` | **무슨 데이터가 어디 있고 어떤 상태인지** | 추적 |

`CATALOG.md` 가 라벨링 장부입니다. 분류(`tourist`/`parking`/`misc`…)와
상태(`raw`→`parsed`→`processed`→`geocoded`→`merged`→`hold`/`reject`)를 표로 기록해,
나중에 기능을 구현할 때 그 파일만 보면 쓸 수 있는 데이터를 찾을 수 있게 했습니다.

## URL 처리

사용자가 메모장으로 URL 을 정리해 줄 때 `---` 로 항목을 구분하기로 했습니다.
블록을 쪼개 URL 을 뽑고, `--fetch` 시 접속해 제목·`Content-Type` 을 확인하고
OpenAPI 링크·`serviceKey` 필요 여부·직접 내려받을 파일 링크 단서를 탐지합니다.
결과는 `data/sources/` 에 JSON 으로 남깁니다.

실측 — `data.go.kr` 공중화장실 표준데이터 페이지에서 OpenAPI·파일링크·상세페이지 단서를 전부 찾아냈습니다.
